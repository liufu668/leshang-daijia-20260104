乐尚代驾
乐尚代驾是一款为用户提供酒后代驾、商务代驾等服务的微信小程序。涵盖乘客端（下单/支付）、司机端（抢单/服务）、管理端（订单监控/司机管理）三大端。
核心技术栈：SpringBoot+SpringCloud(Gateway/Feign)+MyBatisPlus+MongoDB+Redis+RabbitMQ+Redisson

\item 1、关于乘客下单业务,原乘客下单接口全同步执行，存在响应慢、重复调用远程服务、高并发缓存不稳定等问题。
基于 CompletableFuture 实现订单创建与智能派单异步解耦，
主线程同步落库生成订单并返回订单 ID，派单逻辑异步执行，配合定时补偿任务保障派单可靠性。
通过在预估订单阶段提前通过 Redis 缓存路线与费用信息，下单接口优先复用缓存，避免重复的远程服务调用；
为解决高并发下缓存三大问题，采用缓存空值防穿透、分布式锁 + 双重检查防击穿、随机过期时间防雪崩，
同时针对性优化业务线程池与 Redis 连接池参数，消除高并发下资源排队与阻塞。
压测数据：QPS 从 120+ 提升至 250+，平均响应时间从 330ms 降至 150ms。
\item 2、关于司机匹配业务,采用 Redis GEO 结构存储司机实时经纬度信息，支持高效地理位置检索，定时批量同步位置数据至 MongoDB 持久化；
针对原循环远程调用查询司机位置导致接口响应极慢、高并发下性能瓶颈问题，重构核心逻辑为批量查询 + 本地内存过滤模式，彻底消除循环调用开销。
压测数据：QPS从20+提升至230+，性能提升10倍以上，平均响应时间从2.5s优化至200ms，实现高并发下司机秒级精准匹配。
\item 3.关于司机抢单业务,针对高并发抢单场景下重复接单、订单超卖、数据不一致问题，
使用 Lua 原子脚本 校验 Redis 抢单标识并做锁内二次校验，从根源避免重复抢单；
引入 RabbitMQ 实现异步削峰，解耦数据库写入操作，开启生产者 Confirm 机制 + 消费者手动 ACK, 保证消息不丢失、不重复；
基于订单 status 字段保证订单状态机流转顺序，新增 version 字段实现 MySQL 乐观锁，替代数据库悲观锁，彻底解决超卖、重复接单等并发安全问题。
经 160 线程 5 分钟压测，接口稳定 QPS 500+， 业务错误率 0%。

采用优惠券预占机制，创建支付单时仅锁定优惠券资源，支付成功后再进行正式核销；
在支付状态查询中增加支付失败自动释放逻辑，并通过定时任务扫描超时未支付订单，自动关单并回收预占优惠券；
保证订单与优惠券状态一致，避免用户未支付却丢失优惠券、资源长期锁定等资损与体验问题。
\item 5、关于微服务高可用防护设计,针对流量突增、服务抖动可能引发的微服务雪崩问题，

针对乘客下单、司机抢单、司机定位上传等核心高并发接口，单独设置差异化限流阈值，防止流量突洪压垮服务；
同时在 Gateway 网关层配置统一请求限流、黑名单过滤、非法请求拦截，提前筛掉无效请求；
针对 Feign 远程调用超时、服务异常的情况，配置熔断降级.当派单、司机等服务用不了的时候，直接返回预设的兜底结果，阻断故障扩散，

系统整体留有充足的安全冗余，因此没有继续加大线程压力，避免因线程过多导致上下文切换频繁、性能下降的问题。

4 **问题**：订单模块是核心，你说说订单的完整生命周期有哪些状态，怎么管控的？

### 高并发抢单核心（必问）
1 **问题**：你项目里高并发抢单场景的核心问题是什么？怎么一步步解决的？
   **答案**：
高并发抢单场景的核心问题，分为两大方面：
安全问题：归根结底就是数据不一致，具体表现为高并发下订单被多个司机重复接单、超卖；
性能问题：核心是系统吞吐量低，主要是全局锁导致的锁冲突严重，大量请求排队阻塞，系统扛不住高并发。
我分 4 步解决了这些问题：
- 细化分布式锁粒度：把全局锁改成订单级细粒度分布式锁，用 Redisson 实现，从根源上解决锁冲突，提升系统吞吐量；
- 三层状态校验兜底：抢锁前用 Lua 脚本原子性校验 Redis 订单状态，抢到锁后再校验一次，最后更新数据库时 SQL 加状态条件，三层都是校验订单状态，层层拦截，彻底避免重复接单；
- 数据库乐观锁兜底：给 OrderInfo 实体类添加 version 字段，用无阻塞的乐观锁替代悲观锁，既提升性能，又防止数据覆盖；
- 调优系统资源：优化线程池和 Redis 连接池参数，减少线程阻塞和排队，进一步提升系统整体吞吐量。

2 **问题**：为什么用Redisson做分布式锁，而不是自己基于Redis写？Redisson的分布式锁有什么优势？
   **答案**：
自己基于Redis写分布式锁，会遇到**死锁、锁过期被释放、释放别人的锁**三个核心问题，
且需要手动处理锁的续期、异常释放，开发成本高且稳定性差。
Redisson是Redis官方推荐的分布式锁实现，优势很明显：
①自带**看门狗机制**，会自动给持有锁的线程续期，避免锁超时释放；
②提供**isHeldByCurrentThread**方法，能判断当前线程是否持有锁，避免释放其他线程的锁；
③支持**超时自动释放**，即使服务宕机，锁也会在指定时间后释放，避免死锁；
④开箱即用，封装了锁的获取、释放、续期逻辑，企业级规范，比手写更稳定可靠。
项目里用的就是Redisson的可重入锁，锁名拼接订单ID实现细粒度控制。

4 **问题**：为什么要结合**Lua脚本**操作Redis？不用的话会出现什么问题？
   **答案**：
核心原理：Redis 的单条命令是原子的，但 **「多条命令组合」或「Java 端多步骤业务逻辑」是非原子的 **，高并发下会出现竞态条件。
不用 Lua 会出现的问题：
我原本用redisTemplate.hasKey()判断订单可抢标识，hasKey本身是单次EXISTS命令，
但「hasKey判断 → 执行业务抢单逻辑」是 Java 端的多步骤操作，非原子。
高并发下，线程 A 判断订单存在后，线程 B 刚好删除标识，线程 A 仍会继续抢单，导致无效抢单、重复接单。
另外，删除标识时的「先判断存在、再删除」也是非原子操作，会出现竞态，导致误删、漏删。
我项目里的 Lua 用法：
我没有把「判断 + 抢单 + 删除」全打包成一个 Lua（避免 Lua 过长阻塞 Redis），
而是给 **「订单标识原子判断」和「订单标识原子删除」两个关键环节，分别写了独立的 Lua 脚本 **：
判断脚本：把订单存在性校验封装成原子操作，避免 Java 端多步骤的并发误判
删除脚本：把「判断存在 + 删除」打包成原子操作，杜绝删除环节的竞态
Lua 的核心价值：
Lua 脚本可以把多个 Redis 命令打包成一个原子操作，在 Redis 单线程中执行，要么全执行要么全不执行，彻底解决多步骤操作的并发问题，
同时也避免了hasKey在集群模式下的主从一致性问题。

5 **问题**：数据库层面为什么要改**乐观锁（version字段）**，悲观锁的问题是什么？乐观锁的实现原理是什么？
   **答案**：
数据库常用的悲观锁（比如行锁、表锁）是**阻塞式锁**，更新数据时会锁住对应的行/表，其他线程必须等待锁释放才能执行，
高并发写场景下（比如抢单），会导致**数据库线程排队严重、响应慢、吞吐量极低**。
乐观锁是**非阻塞式锁**，基于“乐观估计”，认为并发更新冲突的概率低，不会主动加锁，而是通过**版本号（version）** 实现并发控制，
更适合高并发写场景。
项目里的实现原理：
①给order_info表加version字段，默认值为0；
②更新订单时，把version作为更新条件（where version = 原版本）；
③更新成功的同时，将version自增1（set version = version + 1）；
④如果更新结果行数为0，说明版本号不匹配，有其他线程已更新，抢单失败，直接抛出异常。

6 **问题**：压测时160线程5分钟跑QPS 500+，错误率0%，你是怎么保证压测过程中数据一致性的？有没有遇到过超卖/重复接单的问题，怎么解决的？
   **答案**：

要保证压测过程中的数据一致性，我主要从代码防护和结果校验两方面来保证。
首先在代码层面做了四层并发防护：
第一层用 Redis Lua 原子脚本，把原来的多个 Redis 操作打包成原子操作，要么全部执行，要么都不执行，避免并发竞态问题。
第二层用 Redis 订单级细粒度分布式锁，只有抢同一个订单的线程会竞争锁，不同订单之间互不影响、可以并行执行，
这样既保证了单个订单的并发安全，又不会大面积阻塞线程，能支撑更高的 QPS。
第三层在拿到锁之后，再用 Lua 做一次二次校验，防止等待锁的期间订单已经被抢走，避免极端情况下重复抢单。
第四层引入 RabbitMQ 异步削峰，并开启生产者 confirm 机制，只有 MQ 收到消息并返回 ACK 成功之后，我才去删除 Redis 里的抢单标识，
保证消息可靠和数据一致。
在压测过程中和压测结束后，我会从三个层面排查验证：
第一层查数据库，看最终订单和司机是不是严格一对一，不存在一个订单被多个司机抢到的情况。
第二层看日志：抢单成功才打印订单和司机信息；并发冲突、重复抢单都会抛自定义业务异常。我重点观察同一个订单是不是只有一条成功日志，
其他都是失败拦截日志。
第三层核对Redis 与数据库状态：看 Redis 里的抢单标识是否被正确删除，数据库里订单状态是否同步更新为已接单，保证缓存和库状态一致。
通过代码四层防护 + 三层结果校验，就能保证整个压测过程中数据一致，不会出现超卖和重复接单。

7 **问题**：分布式锁如果出现死锁怎么办？你项目里做了哪些防护？
   **答案**：
我项目里做了四层防护避免分布式锁死锁：
第一，超时自动释放机制（兜底防死锁）,给锁设置 3 秒超时自动释放时间，宕机也能自动释放；
第二，看门狗自动续期机制（防锁提前过期）, 开启 Redisson 看门狗自动续期，防止业务没执行完锁就过期，同时宕机后停止续期，锁最终会释放；
第三，线程持有校验（防误解锁）,解锁前用isHeldByCurrentThread()校验线程持有权，避免误解锁；
第四，把解锁逻辑放在 finally 块，保证无论业务是否异常，锁都能正常释放，彻底杜绝死锁。

### Redis深度应用（外包高频问）
1 **问题**：项目里Redis除了做分布式锁，还用来做什么了？
   **答案**：
在我们代驾项目中，Redis 除了分布式锁，核心落地了两大类场景：
- 高性能缓存(**复用状态**)：
  缓存订单预估里程、费用，设置 15 分钟过期，减少地图 / 计费服务的重复调用；
  用 Redis GEO 存储司机实时经纬度，通过GEORADIUS实现附近司机快速查询，支撑派单；
  存储订单抢单状态标识，快速判断订单是否可抢，抢单成功后删除标识，避免频繁查库。
- 数据结构实现业务队列：用 ZSet 实现延迟队列，处理 15 分钟无人接单的订单自动取消，基于 Redis 原生结构轻量高效，无需额外中间件；
同时用 List 做临时抢单队列，为符合条件的司机推送新订单，司机端轮询拉取，实现高并发场景下的订单分发。
- 分布式状态与锁：用分布式锁解决高并发抢单的超卖问题。

2 **问题**：基于Redis GEO实现司机就近匹配的核心原理是什么？怎么快速查询附近的司机？
   **答案**：
Redis GEO 是专门用于存储和操作地理位置信息的功能，它的核心原理是基于 ** 有序集合（ZSet）** 实现的：
先将经纬度转换为GeoHash 编码，通过编码的前缀匹配来实现附近位置的快速筛选；
利用 ZSet 的有序特性，将 GeoHash 值作为 score 存储，以此来实现距离排序。
在我们代驾项目里，具体实现步骤是：
司机上线后，通过GEOADD命令把司机 ID 和经纬度存入 Redis 的 GEO 集合（key 比如driver:geo:location）；
乘客下单后，调用GEORADIUS命令，以乘客的经纬度为中心，指定 5 公里为半径，查询该范围内的所有司机 ID，
同时返回司机与乘客的距离并按距离排序，优先匹配距离近的司机；
为了提升性能，我们还做了批量查询 + 本地过滤：一次性查出所有附近司机 ID，批量调用司机服务获取订单里程、接单里程等信息，
再在本地过滤出符合条件的司机，减少服务间的循环远程调用。


3 **问题**：项目里用Redis做了订单预估数据的缓存，怎么防止缓存穿透、缓存击穿的？
   **答案**：
为了防止缓存问题，我们项目针对订单预估缓存场景，做了三层针对性设计：
- 缓存穿透防护
对不存在的经纬度路线，采用缓存空对象并设置 2 分钟短过期时间，避免无效请求重复穿透到地图、计费等第三方接口，从根源减少无效调用。
- 缓存击穿防护
针对热点路线缓存失效的高并发场景，采用双重检查 + 轻量级 Redis 分布式互斥锁：
先双重校验缓存状态，再通过 setIfAbsent 抢锁，保证同一时间只有一个请求回源计算；
抢锁失败的请求直接降级返回系统繁忙，不阻塞、不等待，避免大量请求同时压垮第三方服务。
- 缓存雪崩防护
在 15 分钟基础过期时间上，增加 **-1~3 分钟的随机偏移量 **，将缓存过期时间打散为 14~18 分钟，避免大量 key 在同一时间集中失效；
```text

同时依赖 Redis 集群架构，进一步提升缓存服务的高可用性。
我们项目的 Redis 采用了哨兵 + 主从的高可用架构：
1 主 2 从多实例部署，哨兵负责监控主节点状态，自动故障转移，避免单节点宕机导致缓存服务不可用；
同时从节点分担读请求，提升缓存服务的并发能力，从架构层面进一步防止缓存雪崩。
```


4 **问题**：延迟队列用Redisson实现的，原理是什么？为什么不用RabbitMQ的延迟队列？
   **答案**：
Redisson 延迟队列基于 **Redis 有序集合（ZSet）** 实现，核心原理是：
将延迟消息作为 ZSet 的成员，把消息的过期时间戳作为 ZSet 的score；
Redisson 内部会启动一个后台线程定时轮询ZSet，筛选出score小于当前时间戳的过期消息；
过期消息会自动从延迟队列移除，并转入关联的阻塞队列，消费者从阻塞队列获取消息，保证消息只被消费一次。
选择 Redisson 而不用 RabbitMQ 延迟队列的原因：
订单取消属于轻量延时场景，每日订单量不大，Redisson 延迟队列完全能支撑；
Redisson 延迟队列部署简单、轻量，可以复用项目已有的 Redis 组件，无需额外搭建和维护 RabbitMQ 集群，降低运维成本；
RabbitMQ 延迟队列需要配置死信交换机，复杂度高，对于本项目属于 “过度设计”。


5 **问题**：Redis的持久化方式有哪些？项目里用的哪种，为什么？
   **答案**：
Redis 的持久化方式主要有三种：RDB、AOF，以及 RDB+AOF 混合持久化。
RDB：属于全量持久化，它会定时将内存中的所有数据生成快照并保存到硬盘。
优点：数据文件体积小，恢复速度快。
缺点：如果在两次持久化间隔内服务宕机，这段时间的数据会丢失。
AOF：属于增量持久化，它会把每一条写命令追加到 AOF 文件中。
优点：数据安全性更高，能大幅降低数据丢失风险。
缺点：文件体积较大，恢复速度较慢。
混合持久化：
项目中我们采用的是这种模式。
原因是：Redis 缓存的是非核心业务数据，核心数据存储在 MySQL 中，不需要 100% 的数据安全性。
混合模式兼顾了性能与安全：RDB 保证大部分数据不丢失且恢复快，AOF 补充间隔期的增量数据，避免小范围数据丢失，是性价比很高的选择。

### 微服务高可用与性能优化
1 **问题**：项目里怎么保证微服务的高可用？Sentinel做了哪些配置（限流/熔断/降级）？
   **答案**：
项目里主要是通过限流、熔断、降级三部分来保证微服务的高可用性。
第一，限流：针对乘客下单、司机抢单这些高并发核心接口做QPS 限流，超过阈值的请求会被直接拒绝，并返回友好提示，避免流量突增压垮服务。
第二，熔断：对 Feign 远程调用配置慢调用熔断和异常比例熔断，当慢调用比例超过 50%、异常比例超过 20% 时，
Sentinel 会自动熔断该服务，防止一个慢服务或异常服务拖垮整个调用链路，避免服务雪崩。
第三，降级：熔断之后会走兜底降级逻辑，远程调用失败时直接返回默认信息，保证主业务流程不中断，让非核心功能实现优雅降级。

2 **问题**：为什么用CompletableFuture做异步编排？解决了什么问题？和普通线程池有什么区别？
   **答案**：
我使用 CompletableFuture 做异步编排，主要是为了解决下单接口全串行阻塞、响应慢、资源利用率低的问题。
原来的下单流程是同步执行的，订单创建、智能派单等步骤全部串行跑完，接口吞吐量很低。
我通过 CompletableFuture 把订单创建与智能派单做异步解耦：
主线程只负责完成订单落库并返回订单 ID，派单逻辑异步执行；同时通过定时任务兜底，确保即使异步任务失败也能补偿，保证派单可靠性。
相比普通线程池，CompletableFuture 支持更优雅的任务编排、统一异常处理、链式调用，能清晰处理多任务依赖；
再结合自定义线程池做资源隔离，非常适合下单这种复杂业务的异步化改造。


3 **问题**：司机匹配接口一开始性能差，你是怎么优化的？核心思路是什么？
   **答案**：
司机匹配接口最初的性能瓶颈在于：
从 Redis GEO 查到附近司机 ID 后，对每个司机都单独发起一次远程接口调用去获取司机配置，导致大量重复的网络 IO，接口响应时间被严重拉长。
优化思路是：
只调用一次批量远程接口，根据一批司机 ID 一次性查出所有司机配置，拿到数据后在本地内存里做过滤，最后只返回符合条件的司机集合。
这样把 N 次网络 IO 减少到 1 次，极大提升了接口性能。
   

接口性能瓶颈基本都在 IO 上，尤其是循环网络 IO。
我优化思路就是减少 IO 次数、批量请求、本地内存过滤，
把网络 IO 从 N 次降到 1 次，吞吐量自然就上去了。

4 **问题**：项目里有没有遇到过Feign远程调用的问题？（比如反序列化/超时）怎么解决的？
   **答案**：
在使用 Feign 进行微服务调用时，我遇到过 JSON 序列化和反序列化失败 的问题。
虽然项目里已经在 YML 中全局配置了 Jackson 的日期格式和时区，
但在 Feign 调用其他微服务时，日期字段依然解析失败。
后来排查发现，YML 里的 Jackson 配置只对前后端交互、也就是 Controller 层接口生效，
对 Feign 内部的序列化机制是不生效的。
所以最终解决方案是：
在实体类的日期字段上添加 @JsonFormat 注解，统一日期格式和时区，
这样就能保证 Feign 跨服务调用时也能正常解析。
```text

遇到过两个典型问题：
序列化 / 反序列化异常
主要是不同服务之间日期格式不统一，导致 Feign 调用时 JSON 解析失败。
解决方式：
在实体类的日期字段上加 @JsonFormat 注解，指定统一的日期格式和时区
同时在每个服务里全局配置 Jackson，统一所有接口的日期格式与时区
核心就是：保证多个微服务之间序列化、反序列化规则完全一致。
Feign 调用超时问题
有些接口响应慢，导致调用方超时报错，甚至影响整个链路。
解决方式：
在配置文件里自定义 Feign 的连接超时和读取超时
配合 Sentinel 针对超时、慢调用做熔断降级
避免一个慢服务拖垮整个应用，保证系统高可用。
```

5 **问题**：数据库层面做了哪些优化？（索引/乐观锁/批量操作）
   **答案**：
项目里针对数据库做了多层优化，核心围绕**提升查询速度、减少阻塞、降低数据库压力**：
①**索引优化**：给核心表的查询字段、关联字段、状态字段加索引， 
比如order_info表的id、customer_id、driver_id、status字段加主键/普通索引，
driver_info表的wx_open_id加唯一索引，让查询从全表扫描变为索引扫描，查询速度提升80%以上；
②**锁机制优化**：将高并发写场景的悲观锁替换为**乐观锁（version）**，实现无阻塞并发更新，提升数据库吞吐量；
③**批量操作优化**：用MyBatis-Plus的**批量插入/更新**方法，替换循环的单条插入/更新，
减少数据库的连接次数和SQL执行次数（比如批量保存司机登录日志，一次批量操作替代100次单条插入）；
④**SQL优化**：避免大SQL、联表查询、子查询，将复杂查询拆分为多个小查询；避免SELECT *，只查询需要的字段，减少数据传输量；
⑤**分表分库思路**：针对订单表这类海量数据量表，预留了按**时间分表**（按月份拆分为order_info_202601、order_info_202602）的方案，
避免单表数据量过大导致的性能下降。

- 只要是同一个数据库里，同时操作多张表的新增、修改、删除，一律加上 @Transactional 事务注解，准没错。
因为事务开销很小，却能避免绝大多数数据不一致问题，后期维护也更安全。只有纯查询、日志类、高并发非核心接口，才会考虑不加或加只读事务。
- 针对原代码中循环远程调用、循环查询数据库的性能瓶颈，我把多次单条查询重构为批量查询模式，比如司机匹配业务中，
将循环查询司机位置改为一次批量拉取， 再在本地内存做过滤，大幅减少了数据库 IO 次数和网络开销。
- 给核心业务表（比如 order_info、driver_info）的高频查询字段、关联字段、状态字段添加索引，把全表扫描优化为索引扫描，提升查询效率；
同时在司机抢单这类高并发写场景，给 order_info 表新增 version 字段，用MySQL 乐观锁替代数据库悲观锁，实现无阻塞并发更新，
彻底解决了订单超卖、重复接单的问题，提升了数据库吞吐量。
- 除此之外，我还做了 SQL 规范优化，比如避免SELECT *、只查需要的字段，减少数据传输量；
用 MyBatis-Plus 的批量插入替代循环单条插入，进一步降低数据库压力。
- 除了这三点，我还做了这些优化：
SQL 规范优化：避免SELECT *，只查询需要的字段，减少数据传输量；避免大表联查，把复杂查询拆成多个小查询，用 Redis 缓存中间结果；
连接池优化：调整 Druid 连接池参数（比如最大连接数、等待超时时间），避免数据库连接耗尽导致的服务宕机；
慢查询优化：开启 MySQL 慢查询日志，定期排查慢 SQL，针对性加索引、优化 SQL，把慢查询从秒级优化到毫秒级。

### 实际问题排查与解决（外包超看重）
1 **问题**：项目开发过程中遇到的最难的技术问题是什么？怎么排查和解决的？
   **答案**：
最难的是**高并发抢单场景的超卖问题**，开发初期用全局锁+Redis非原子操作，压测时出现多个司机抢同一个订单的情况，且难以复现和定位。
排查步骤：①**日志排查**：在抢单的关键节点（获取锁、Redis判断、数据库更新）添加详细日志，记录线程ID、订单ID、操作时间，
压测后通过日志分析，发现多个线程同时进入了抢单逻辑；②**代码走查**：检查Redis操作和分布式锁代码，
发现Redis的exists和del是分开执行的非原子操作，且用了全局锁，高并发下锁冲突严重；
③**压测复现**：用JMeter搭建100线程的压测环境，稳定复现超卖问题，确定问题根源。
解决方法：一步步落地了Redisson细粒度分布式锁、Lua脚本原子操作、订单状态机+MySQL乐观锁的三重防护方案，
压测验证后超卖问题彻底解决，160线程5分钟压测错误率0%。

2 **问题**：压测时发现接口性能瓶颈，你是怎么定位的？（从应用/缓存/数据库哪个层面入手）
   **答案**：
压测时通过**“从应用到缓存再到数据库”** 的分层排查思路定位性能瓶颈，配合**日志监控、数据库慢查询、Redis监控**工具：
①**应用层排查**：查看服务的运行日志，统计每个方法的执行时间，发现司机匹配接口的循环远程调用方法执行时间长达2s，是明显的性能瓶颈；
同时检查线程池状态，发现核心线程数不足，导致任务排队，调优线程池参数后缓解。
②**缓存层排查**：通过Redis的info命令查看监控指标，发现Redis的命中率偏低，原因是部分热点数据未缓存，添加缓存后命中率提升至95%以上；
同时发现Redis的连接数不足，调优Redis连接池参数（最大活跃50），避免连接排队。
③**数据库层排查**：开启MySQL的慢查询日志，捕获执行时间超过100ms的慢SQL，发现部分查询未走索引，添加索引后慢SQL消失；
同时发现数据库的连接池数不足，调优后避免数据库连接阻塞。分层排查能快速定位瓶颈，避免盲目优化，提升优化效率。

3 **问题**：微信小程序对接时有没有遇到过问题？（比如登录授权/手机号获取）怎么解决的？
   **答案**：
遇到过**微信小程序手机号获取失败**和**微信授权code过期**两个问题。
①微信小程序手机号获取失败：原因是个人微信小程序**不支持获取真实手机号**，微信官方限制，只能获取到虚拟手机号。
解决方法：做了**模拟处理**，在后端生成随机手机号（138+8位随机数），直接更新到数据库，满足开发和测试需求；
如果是企业小程序，只需按微信官方文档，用手机号授权码调用API即可获取真实手机号。
②微信授权code过期：原因是微信的登录code**有效期只有5分钟**，且只能使用一次，前端未及时将code传给后端，或重复使用code。
解决方法：一是在前端添加**code过期提示**，获取code后立即调用后端登录接口，避免过期；
二是在后端添加**code使用校验**，调用微信API换取openid时，如果返回code过期/已使用，直接抛出异常，提示前端重新获取code；
同时在后端记录code的使用日志，方便问题排查。

4 **问题**：分布式场景下，订单状态更新不一致怎么办？你项目里怎么保证的？
   **答案**：
分布式场景下，订单状态更新不一致的主要原因是**微服务间调用异常、网络波动、并发更新**，
项目里通过**“状态机管控+事务保证+消息补偿+日志追溯”** 四层方案保证状态一致性：
①**订单状态机**：严格管控订单状态的流转，每个状态只能按指定流程更新，更新时必须校验原状态，避免非法状态变更；
②**本地事务**：订单状态更新的核心逻辑（比如抢单、司机到达）都放在本地事务中，保证数据库操作的原子性，要么全部成功，要么全部回滚；
③**消息补偿**：对于跨服务的状态更新（比如支付成功后更新订单状态），用RabbitMQ发送**可靠消息**，如果消费失败则自动重试，
保证消息最终被消费；
同时添加补偿任务，定时扫描异常订单（比如待付款但超过30分钟未支付的订单），手动更新状态；
④**日志追溯**：订单的每一次状态变更都记录到**订单状态日志表**，包含订单ID、原状态、新状态、操作时间、操作人，
方便问题排查和数据追溯，即使出现状态不一致，也能通过日志快速定位并修复。

### 拓展与技术理解
1 **问题**：项目里用了MongoDB，什么场景下用的？为什么不用MySQL？
   **答案**：
项目里用MongoDB存储**司机代驾的GPS轨迹数据**和**代驾监控的录音日志、对话文本**，
这些是**非结构化/半结构化、海量、写密集、查询以范围查询为主**的场景，不适合用MySQL。
原因：①MySQL是关系型数据库，适合存储结构化、有严格关联关系的数据，存储非结构化数据需要用BLOB/TEXT类型，查询和存储效率低；
②GPS轨迹数据是海量的，司机每秒钟都会产生一条定位数据，用MySQL存储会导致**单表数据量快速膨胀**，超过千万行后查询速度急剧下降，
而MongoDB是文档型数据库，支持**水平扩展**，能轻松支撑海量数据存储；
③MongoDB支持**地理空间索引**，能快速查询指定时间范围内的GPS轨迹，适合代驾里程计算的场景；
④MongoDB的写性能远高于MySQL，支持高并发的写操作，适合日志、轨迹这类写密集的场景。而订单、司机、用户等核心结构化数据，
仍用MySQL存储，保证数据的一致性和事务性。

2 **问题**：MinIO在项目里的作用是什么？和腾讯云COS的区别是什么？
   **答案**：
MinIO在项目里是**轻量级对象存储**，主要存储代驾过程中的**司机拍照的车辆照片、代驾录音文件、司机认证的证件照片**等二进制文件
，替代了传统的本地文件存储，支持分布式部署，保证文件的高可用。MinIO和腾讯云COS的核心区别：
①**部署方式**：MinIO是**开源的本地对象存储**，部署在自己的服务器上，数据归自己管理，无需依赖第三方云服务；
腾讯云COS是**云对象存储**，部署在腾讯云服务器上，数据存储在云端，依赖第三方服务。
②**使用成本**：MinIO开源免费，只有服务器硬件成本，无后续使用费用；
腾讯云COS按**存储量、流量、请求数**计费，长期使用有一定成本。
③**运维成本**：MinIO部署简单，轻量级，适合中小型项目，运维成本低；
腾讯云COS无需自己运维，由腾讯云负责，但需要熟悉云服务的配置和计费规则。
④**功能丰富度**：腾讯云COS功能更丰富，支持CDN加速、数据备份、内容审核等；
MinIO功能简洁，聚焦于对象存储的核心需求，满足项目的基本文件存储需求。项目里开发测试阶段用MinIO，生产环境可无缝切换为腾讯云COS，
无需修改代码。

3 **问题**：什么是服务雪崩？怎么防止？项目里做了哪些措施？
   **答案**：
服务雪崩是指微服务架构中，**一个核心服务宕机或响应缓慢**，导致依赖该服务的其他服务也出现请求阻塞、线程耗尽，
最终引发整个调用链的服务瘫痪，就像雪崩一样层层蔓延。防止服务雪崩的核心思路是**「限流削峰、熔断隔离、降级兜底、服务高可用」**，
项目里做的具体措施：①**限流**：用Sentinel对核心接口做QPS限流，避免大量请求涌入，压垮服务；
②**熔断**：对Feign远程调用做慢调用/异常熔断，当一个服务调用失败/超时时，自动熔断该服务的调用，避免请求一直阻塞，占用线程资源；
③**降级**：熔断后做兜底降级，返回默认数据或友好提示，保证主业务流程不中断，非核心功能优雅降级；
④**服务隔离**：核心服务多实例部署，通过Nacos实现服务发现和健康检查，一个实例宕机后流量自动转发到其他实例；
同时为核心服务分配独立的线程池，避免非核心服务的线程耗尽影响核心服务；
⑤**资源调优**：调优线程池、Redis连接池、数据库连接池的参数，避免资源耗尽导致的服务阻塞；
⑥**缓存复用**：将高频调用的服务数据缓存到Redis，减少对下游服务的调用，降低服务依赖。

4 **问题**：如果你要优化这个项目的并发能力，下一步会从哪些方面入手？
   **答案**：
如果继续优化项目的并发能力，会从**缓存、数据库、微服务、消息队列**四个核心方向入手，结合项目的业务场景做深度优化：
①**缓存深度优化**：引入**缓存预热**，将热点订单、热点司机数据提前加载到Redis缓存，避免高并发下缓存击穿；
同时引入**缓存穿透的高级防护**，用布隆过滤器替代缓存空值，进一步降低数据库压力；
还可以用**Redis集群**做分片，提升缓存的读写性能和容量。
②**数据库优化**：对订单表、司机表做**分表分库**，订单表按时间分表，司机表按地区分库，避免单表/单库数据量过大导致的性能下降；
引入**读写分离**，将查询请求转发到从库，写请求转发到主库，提升数据库的查询性能。
③**微服务优化**：引入**服务网格（Istio）**，实现更精细化的服务治理、流量控制和熔断降级；
将核心的抢单、下单逻辑做**服务无状态化**，支持水平扩容，通过增加服务实例提升并发能力；
还可以引入**分布式事务（Seata）**，解决跨服务的事务一致性问题，支撑更高的并发写场景。
④**消息队列优化**：将更多的同步调用改为**异步消息调用**，比如订单创建后的派单、日志记录、消息推送等，
用RabbitMQ做异步解耦，提升主流程的响应速度；引入**消息削峰填谷**，在下单高峰期，用消息队列缓冲订单请求，避免直接压垮核心服务。
⑤**硬件和部署优化**：对核心服务的服务器做**硬件升级**（提升CPU、内存、带宽）；用Docker+Kubernetes做容器化部署和自动扩缩容，
根据流量自动增加/减少服务实例，实现弹性伸缩。
