2  **ConcurrentHashMap 1.8为什么用synchronized？和ReentrantLock区别？**
1）ConcurrentHashMap 1.8 用 synchronized 最重要原因：锁粒度变小了！
1.7 是Segment 分段锁（锁一大段）
1.8 是锁桶头节点（只锁一个链表 / 树的头节点）
锁粒度极小，并发极高！
2）JDK 1.6 以后 synchronized 已经被官方 heavily optimize 了
偏向锁 → 轻量级锁 → 重量级锁
高并发下性能并不比 ReentrantLock 差！
3）ConcurrentHashMap 1.8 用 synchronized + CAS 配合
查：用 CAS 无锁
改：用 synchronized 锁桶头
这才是它高性能的关键。
三、我帮你整理成【最终满分版】（你直接背这一段）
ConcurrentHashMap 1.8 放弃了 1.7 的 Segment 分段锁，改为 CAS + synchronized 锁桶头节点，锁粒度从分段缩小到哈希桶头部，并发性能大幅提升。
同时 JDK 1.6 后 synchronized 做了大量锁优化，性能已非常接近 ReentrantLock，而且代码更简洁、不用手动 unlock，不容易出错。
synchronized 和 ReentrantLock 的区别：
synchronized 是 JVM 内置隐式锁，自动加锁释放，不可中断、只能非公平；
ReentrantLock 是 JDK 层面显式锁，支持可中断、tryLock 尝试获取、公平锁、多 Condition 精准唤醒。
使用场景：
简单场景、小粒度锁用 synchronized；
需要灵活控制、高并发复杂场景用 ReentrantLock。

```text
    // 业务逻辑
}
```

```text
二、常用写法 1：Java 代码自定义线程池（生产主流）
实际开发很多场景会手动创建ThreadPoolExecutor，精准管控参数，完整示范代码
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import java.util.concurrent.*;

@Configuration
public class ThreadPoolConfig {

    // 自定义订单业务线程池
    @Bean("orderThreadPool")
    public ExecutorService orderThreadPool() {
        // 七大参数依次赋值
        int corePoolSize = 30;                 // 1.核心线程数
        int maximumPoolSize = 100;             // 2.最大线程数
        long keepAliveTime = 60;               // 3.空闲存活时间
        TimeUnit unit = TimeUnit.SECONDS;      // 4.时间单位
        // 5.阻塞队列：容量500
        BlockingQueue<Runnable> workQueue = new ArrayBlockingQueue<>(500);
        // 6.线程工厂：自定义线程名称，方便日志排查
        ThreadFactory threadFactory = new ThreadFactoryBuilder()
                .setNameFormat("order-business-thread-%d")
                .build();
        // 7.拒绝策略：默认AbortPolicy抛异常，也可按需切换
        RejectedExecutionHandler handler = new ThreadPoolExecutor.AbortPolicy();

        // 创建线程池
        return new ThreadPoolExecutor(
                corePoolSize,
                maximumPoolSize,
                keepAliveTime,
                unit,
                workQueue,
                threadFactory,
                handler
        );
    }
}

import org.springframework.context.annotation.Configuration;
import org.springframework.scheduling.annotation.EnableAsync;

import java.util.concurrent.Executor;

        // 对应七大参数

        // 拒绝策略
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        executor.initialize();
        return executor;
    }
}
```

6  **CompletableFuture为什么比@Async好？异常怎么处理？**
先给你一句终极结论（背它）
CompletableFuture 比 @Async 强在：灵活、可编排、支持异步链式调用、能精准控制异常。
@Async 只是简单异步，复杂场景完全不够用。
一、CompletableFuture 为什么比 @Async 好？（面试满分回答）
我给你4 个最核心、最加分、面试官最爱听的理由：
1）支持异步编排（最关键！）
你可以 A 执行完再执行 B
你可以 A 和 B 并行执行，最后合并结果
你可以 等待所有任务完成
你可以 任何一个完成就继续
@Async 做不到！@Async 只能单独跑，不能编排！
2）功能更强大：thenApply /thenAccept/thenRun /allOf/anyOf
CompletableFuture 有一整套异步流式 API，
像写流水线一样写代码。
@Async 只有 “异步跑一下”，没有后续流程。
3）异常处理更灵活、更精准
CompletableFuture 可以：
单独捕获某个异步任务异常
异常后降级
异常后继续执行
@Async 异常很难捕获，必须全局捕获，不精细。
4）不依赖 Spring，通用性更强
CompletableFuture 是 JDK 原生类，
任何项目都能用。
@Async 是 Spring 专属，离开 Spring 就废。
二、一句话总结（面试直接说）
CompletableFuture 是真正的异步编排工具，
@Async 只是简单异步注解。
复杂业务、多异步任务、并行、依赖、聚合，必须用 CompletableFuture。
三、CompletableFuture 异常怎么处理？（背这 3 种）
CompletableFuture 异常处理非常清晰，面试必考。
```text
1）exceptionally —— 异常捕获 + 降级返回
future.exceptionally(ex -> {
    // 异常了，返回默认值
    return "默认结果";
});
2）handle —— 无论正常 / 异常都进入（万能处理）
future.handle((result, ex) -> {
    if(ex != null) {
        return "异常降级";
    }
    return result;
});
3）whenComplete —— 只处理，不修改返回值
future.whenComplete((result, ex) -> {
    if(ex != null) {
        log.error("异常", ex);
    }
});
```

# 二、Spring + SpringBoot（第二轮必深挖）
1  **Spring IOC、Bean生命周期、AOP底层？**
先把核心讲透：Spring Bean 生命周期主流分 7 步，不是凭空定的，是按「实例创建 → 属性填充 → 初始化 → 销毁」完整流程划分，结合源码执行顺序、代码示例、每一步作用帮你理解，同时区分易混点。
一、先明确标准 7 步（面试通用版本，按执行顺序）
实例化（创建对象）
属性填充（依赖注入）
Aware 接口回调（感知容器 / 自身信息）
前置初始化（BeanPostProcessor 前置处理）
初始化方法（InitializingBean + @PostConstruct + init-method）
后置初始化（BeanPostProcessor 后置处理）
销毁（容器关闭时执行 @PreDestroy + destroy-method）
补充：容器启动到可用，是前 6 步；容器关闭触发第 7 步。
二、逐步拆解：为什么要有这一步？作用是什么？
结合执行逻辑，从程序运行角度解释，不再死记硬背。
1. 实例化：new 对象
动作：Spring 通过反射调用构造方法，把 Bean 实体创建出来。
为什么需要？任何对象使用前，第一步必然是开辟内存、创建实例，这是 Java 基础逻辑。
举例：OrderService 先通过无参 / 有参构造 new 出对象。
2. 属性填充：依赖注入（DI）
动作：自动给对象的成员变量赋值，比如 @Autowired、@Resource、set 方法注入。
为什么排在实例化之后？对象都没创建，没法给属性赋值，逻辑顺序不可逆。
对应你的项目：@Autowired private RedisTemplate redisTemplate，这一步完成注入。
3. Aware 系列接口回调
常见：BeanNameAware(获取 Bean 名称)、BeanFactoryAware(获取 Bean 工厂)、ApplicationContextAware(获取 Spring 容器)
动作：Spring 把容器内部信息、Bean 名称回传给当前 Bean。
为什么放在注入之后？必须先把依赖注入完成，Bean 状态稳定了，再让它感知容器信息；如果提前执行，属性还没赋值，感知也无意义。
场景：业务中需要主动获取容器内其他 Bean 时，会用到这些接口。
4. BeanPostProcessor 前置处理
动作：Spring 全局后置处理器，在正式初始化之前，对 Bean 做统一加工（比如动态代理、属性修改）。
为什么在 Aware 之后、初始化之前？
此时：对象创建完、属性注满、也感知了容器，状态完整。
先统一预处理，再执行 Bean 自身的初始化逻辑，分层清晰。
核心：这是容器层面的通用处理，不属于单个 Bean 自己的逻辑。
5. 执行初始化方法（单个 Bean 自定义初始化）
执行顺序：@PostConstruct → InitializingBean#afterPropertiesSet() → 配置的 init-method
动作：开发者自定义逻辑，比如加载缓存、初始化连接、校验参数等。
为什么放在前置处理器之后？
容器先做通用处理，再执行当前 Bean 独有的初始化业务，职责拆分。
场景：你的项目中，Bean 启动时预加载字典数据，就写在这里。
6. BeanPostProcessor 后置处理
动作：初始化完成后，容器再做一轮统一加工（Spring AOP 动态代理主要在这里生成）。
逻辑：Bean 自身初始化完毕，最后由容器做收尾加工，之后 Bean 正式就绪，对外提供服务。
7. 销毁方法
执行顺序：@PreDestroy → 配置的 destroy-method
动作：Spring 容器关闭（如项目停机）时执行，释放资源。
为什么放最后？Bean 整个生命周期结束，不再对外提供服务，需要关闭连接、清空缓存、释放线程等。
三、一句话串起完整逻辑（帮你记忆）
先造对象 → 再赋值依赖 → 让它认识容器 → 容器先预处理 → 自己做初始化 → 容器最后加工 → 停机释放资源
整个流程遵循：先基础构建 → 再感知环境 → 容器通用处理 → 自身业务初始化 → 最终可用 → 下线销毁，完全符合程序运行的自然顺序。
四、极简代码演示（运行就能看到执行顺序，直观理解）
```text
import org.springframework.beans.BeansException;
import org.springframework.beans.factory.*;
import javax.annotation.PostConstruct;
import javax.annotation.PreDestroy;

public class LifeCycleDemo implements BeanNameAware, BeanFactoryAware, InitializingBean, DisposableBean {

    // 1. 实例化：构造方法
    public LifeCycleDemo() {
        System.out.println("1. Bean 实例化（构造方法）");
    }

    // 2. 依赖注入（模拟属性填充，Spring自动执行）
    private String name;
    public void setName(String name) {
        this.name = name;
        System.out.println("2. 属性填充 / 依赖注入");
    }

    // 3. Aware 接口回调
    @Override
    public void setBeanName(String s) {
        System.out.println("3. BeanNameAware 回调");
    }
    @Override
    public void setBeanFactory(BeanFactory beanFactory) throws BeansException {
        System.out.println("3. BeanFactoryAware 回调");
    }

    // 5. 初始化注解
    @PostConstruct
    public void postConstruct() {
        System.out.println("5. @PostConstruct 初始化");
    }

    // 5. InitializingBean 初始化
    @Override
    public void afterPropertiesSet() throws Exception {
        System.out.println("5. InitializingBean#afterPropertiesSet");
    }

    // 7. 销毁注解
    @PreDestroy
    public void preDestroy() {
        System.out.println("7. @PreDestroy 销毁");
    }

    // 7. DisposableBean 销毁
    @Override
    public void destroy() throws Exception {
        System.out.println("7. DisposableBean#destroy");
    }
}
```

五、面试精简回答（结合理解背诵）
实例化：通过反射调用构造方法创建 Bean 实例；
属性填充：完成依赖注入，给成员变量赋值；
Aware 接口：让 Bean 感知自身名称、Spring 容器等信息；
BeanPostProcessor 前置处理：容器层面对 Bean 做统一预处理；
初始化：依次执行@PostConstruct、afterPropertiesSet、init-method，执行自定义初始化逻辑；
BeanPostProcessor 后置处理：容器二次加工，完成动态代理等操作，Bean 正式可用；
销毁：容器关闭时，执行@PreDestroy、destroy-method，释放资源。
整体流程遵循先构建对象、再完善属性、最后初始化使用、停机销毁的逻辑，每一步都有明确职责。
六、补充两个高频疑问（避坑）
为什么初始化方法不能放在注入之前？
初始化逻辑大概率会用到注入的属性，属性没赋值，代码会空指针，所以注入必须在前。
BeanPostProcessor 是什么角色？
全局 “加工器”，所有 Bean 都会经过它，所以放在 Bean 自身逻辑的前后，做统一增强。

以Bean 自身状态变化为主线，按「从无到有、从创建到销毁」梳理，结合 7 步生命周期，每一步讲清 Bean 本身发生了什么，逻辑连贯好理解。
整体主线
无对象 → 空对象 → 赋值完成的完整对象 → 可正常工作的成熟对象 → 待回收对象
1. 实例化（第一步）
状态：内存中诞生一个空实例
动作：Spring 反射调用构造方法，堆内存开辟空间，创建出 Bean 对象。
变化：从 0 → 有对象，但此时对象的成员变量全是默认值（null、0 等），还没有业务数据和依赖。
类比：造出了一个空盒子，盒子里啥都没有。
2. 属性填充 / 依赖注入（第二步）
状态：空实例 → 属性齐全的完整实例
动作：给 @Autowired、配置属性等逐一赋值，注入容器中的其他 Bean、配置参数。
变化：对象的成员变量全部初始化完毕，依赖关系全部建立。
类比：往空盒子里放入各种工具、配件，盒子现在 “装备齐全”。
关键点：这一步之后，对象具备了运行的基础条件。
3. Aware 接口回调（第三步）
状态：完整实例 → 感知容器的实例
动作：Spring 把 Bean 名称、容器对象等信息回传给当前 Bean。
变化：Bean 知道了 “我是谁”、“我在哪个容器里”，拥有了和 Spring 容器交互的能力。
类比：盒子贴上身份标签，并且知道自己放在哪个仓库里。
4. BeanPostProcessor 前置处理（第四步）
状态：基础完备实例 → 被容器预处理的实例
动作：Spring 全局处理器对 Bean 做统一修改、包装。
变化：对象本身逻辑不变，但被容器做了前置增强（比如修改属性、标记状态）。
类比：仓库管理员对盒子做初步检查、规整。
5. 执行初始化方法（第五步）
状态：预处理实例 → 完成自定义初始化的实例
动作：执行 @PostConstruct、afterPropertiesSet、init-method 等开发者自定义逻辑。
变化：Bean 执行自身业务初始化（加载缓存、创建连接、校验数据等），内部业务状态就绪。
类比：盒子里的工具通电、调试，完成开工前准备。
6. BeanPostProcessor 后置处理（第六步）
状态：初始化完成实例 → 最终成品 Bean（对外提供服务）
动作：容器做最后加工，最典型就是生成 AOP 动态代理对象。
变化：部分 Bean 会被替换为代理对象；至此 Bean 彻底就绪，正式对外提供服务，接收请求、执行业务。
类比：盒子最终封装完毕，上架投入使用。
7. 销毁（第七步，容器关闭时触发）
状态：服务中 Bean → 待销毁对象
动作：执行 @PreDestroy、destroy-method，执行资源释放逻辑。
变化：关闭连接、清空缓存、释放线程等，业务状态全部回收。最终对象失去作用，等待 JVM 垃圾回收。
类比：项目停机，盒子里工具断电、收纳，整个生命周期结束。
一句话串联（方便口述 / 记忆）
先是凭空创建出空对象，接着给对象补齐所有依赖和属性，然后让它识别容器与自身信息，经过容器两轮加工后，再完成自身业务初始化，最终变成可对外服务的完整 Bean；等到容器关闭，就释放资源、等待回收。

OOP（面向对象）：纵向划分
按业务模块 / 类拆分代码，是纵向层级。
比如代驾项目：订单类、司机类、支付类，各司其职，代码从上到下聚焦核心业务。
AOP（面向切面）：横向切割
很多通用功能（日志、权限、事务、限流、监控），会横跨多个业务类 / 方法。
把这些散落在各处的通用代码，单独抽出来形成一个独立的 “面”，这个独立的功能面，就叫 切面 (Aspect)。

AOP核心术语:
* 切面 (Aspect)：就是我们写的通用功能类（日志切面、事务切面），承载横向逻辑；
* 连接点 (JoinPoint)：主干上可以被切面切入的位置（所有方法、异常点等）；
* 切入点 (Pointcut)：筛选规则，指定哪些方法要被切面增强；
* 通知 (Advice)：切面里具体要执行的逻辑（前置、后置、环绕、异常通知）；
* 织入 (Weaving)：把切面代码，横向嵌入到目标方法的过程。

2  **SpringBoot自动配置原理、@Conditional注解？**
Spring Boot 自动配置由启动注解 @SpringBootApplication 中的 @EnableAutoConfiguration 开启。
它通过 SPI 读取 META-INF 下的自动配置清单，加载一系列自动配置类。
再依靠 @Conditional 系列条件注解判断运行环境，满足条件就自动生成 Bean 并注入 IOC 容器。
同时框架设计了优先级规则，我们手动定义的配置和 Bean，会优先于默认自动配置生效，以此实现灵活的按需装配。

3  **Spring事务传播机制、REQUIRED/REQUIRES_NEW区别？**
REQUIRES_NEW 和 NESTED 最大差别
REQUIRES_NEW：两个独立事务，彻底隔离；
NESTED：一个主事务 + 多个子事务，外层强约束内层。

4  **@Transactional失效场景（最常问）？**
Spring 的声明式事务 @Transactional，本身就是用 AOP 实现的，所以事务失效，本质就是 AOP 没生效。

我们写的业务类 / 实现类，打上组件注解后，被 Spring 扫描、实例化，变成 IOC 容器中的 Bean。
如果这个 Bean 需要 AOP 增强（事务、日志等），Spring 会在运行时生成动态代理：
类有接口 → 用 JDK 代理（基于接口）
类无接口 → 用 CGLIB 代理（基于类继承）
最终容器里对外提供的，是代理对象，原生对象被包裹在内部。
外部代码调用 Bean，走代理 → AOP / 事务生效；
同类内部用 this 调用，直接访问原生对象，绕开代理 → AOP / 事务失效。
像数据库实体这类纯数据类，一般不作为 Bean，自然也不会被代理。

IOC 里所有 Bean 都是类实例化出来的对象，不存在脱离类的 Bean；接口本身不能成为 Bean，我们只是用接口引用指向它的实现类对象。
容器里的 Bean 来源很广，不只是日常写的 Service、Controller。

Spring 事务 = 用 AOP 在方法执行前后，自动帮你写 3 行代码：开启事务、提交事务、异常回滚事务。
AOP 只是执行时机的工具，事务是里面写的具体代码逻辑。
1. 先分开两个东西
AOP（面向切面）：只负责一件事
拦截方法，在方法执行前、执行后、抛异常时插入代码。
它本身不懂什么是事务，只是个 “代码插入工具”。
事务（保证一致性）：是一段数据库逻辑
方法前：begin 开启事务
正常结束：commit 提交
抛异常：rollback 回滚
Spring 做的事就是：用 AOP 把这三行事务代码，自动插到你的方法外面。
2. 伪代码演示：Spring 底层真实逻辑（最关键）

```text
Spring 通过 AOP + 动态代理，自动给你包了一层代码，真实运行代码是这样：
```

5  **SpringMVC执行流程？**
核心一句话：请求→前端控制器分发→处理器映射→处理器适配器→执行业务→视图解析→渲染页面→响应
下面给你最标准、最精简、面试必背 8 步，通俗好记：
1. 客户端发起请求
浏览器发送请求，访问后端接口。
2. 到达 DispatcherServlet（前端控制器，入口）
所有请求先统一交给 DispatcherServlet，它是 SpringMVC 的总调度中心。
3. 调用 HandlerMapping（处理器映射器）
根据请求 URL，找到对应的 Controller（处理器），返回处理器执行链。
4. 调用 HandlerAdapter（处理器适配器）
适配 Controller，让框架能调用 Controller 里的方法（因为 Controller 写法多样）。
5. 执行 Controller 业务逻辑
Controller 处理请求，调用 Service，处理数据，返回 ModelAndView（数据 + 视图名）。
6. ViewResolver（视图解析器）
根据视图名，解析成真实物理视图（如 jsp/html）。
7. 视图渲染
把 Model 数据填充到视图中。
8. 响应结果
把最终页面 / JSON 数据返回给浏览器。

超精简背诵版（一句话版，面试直接说）
客户端请求先经过 DispatcherServlet，通过 HandlerMapping 找到 Controller，HandlerAdapter 调用 Controller 执行业务，
返回 ModelAndView；再由 ViewResolver 解析视图、渲染，最终响应给客户端。

# 三、微服务（SpringCloud）
1  **Nacos注册/配置中心原理、和Eureka区别？**
一、Nacos 注册中心核心原理
它解决的是微服务里「服务之间怎么互相找到」的问题，核心流程分为 3 步：
1 服务注册
微服务启动时，会把自己的信息（IP、端口、服务名等）发送给 Nacos 服务端
Nacos 收到后，把这些实例信息存到内存的「服务注册表」中
客户端会定期发送心跳包，证明自己还活着；Nacos 会把长时间没心跳的实例标记为不健康或剔除
2 服务发现
服务消费者会从 Nacos 获取对应服务的实例列表
Nacos 支持两种模式：
拉模式（Pull）：客户端定时主动拉取最新的实例列表
推模式（Push）：服务端实例变更时，主动把变化推送给客户端，实时性更高
3 集群一致性
Nacos 集群间通过 Raft 协议 保证数据一致性
写请求由 Leader 节点处理，再同步给其他 Follower 节点，保证 CP 模式下的数据强一致
二、Nacos 配置中心核心原理
Nacos 同时也是配置中心，解决的是「多环境、多服务的配置统一管理」问题：
配置存储：配置以 Data ID + Group + Namespace 为唯一标识，支持多环境隔离
配置获取：服务启动时，从 Nacos 拉取对应配置，加载到本地
配置动态更新：配置变更时，Nacos 会主动推送给客户端，客户端可以热更新配置，无需重启服务
三、Nacos 与 Eureka 的核心区别（面试高频）
表格
对比维度	Eureka	Nacos
功能范围	仅支持服务注册与发现	同时支持服务注册 / 发现 + 配置中心，一站式解决方案
CAP 模型	仅支持 AP 模式，优先可用性，最终一致性	支持双模式： 临时实例：AP 模式（高可用）;持久化实例：CP 模式（强一致）
健康检查	仅依赖客户端心跳	支持客户端心跳、服务端主动探测、用户自定义健康检查
配置管理	不支持，需配合 Spring Cloud Config 等组件	原生支持配置中心，支持动态刷新、灰度发布、多环境隔离
一致性协议	无内置一致性协议，靠客户端缓存保证高可用	CP 模式下使用 Raft 协议 保证集群数据强一致
适用场景	简单微服务架构，只需要基础服务发现	中大型微服务架构，需要服务治理、配置管理等综合能力
四、面试一句话总结（直接背）
Nacos 是一个同时支持服务注册发现和配置管理的平台，服务通过心跳注册到 Nacos 集群，消费者通过拉取或推送的方式获取服务列表； 
它比 Eureka 功能更全面，支持 AP/CP 双模式和动态配置刷新，更适合复杂的微服务架构。
2  **Gateway和Zuul区别、Gateway核心功能？**
Zuul1 基于同步 Servlet 阻塞模型，性能弱、编码繁琐，现已淘汰；
Gateway 基于 Netty 异步非阻塞，高并发性能更强，过滤器写法简洁、原生支持动态路由和 WebSocket，是目前 SpringCloud 主流网关。

二、整条 Gateway 连贯逻辑（down 底层 + up 落地，面试一整条口述）
down（底层原理）
Gateway 基于 Spring5+WebFlux+Netty 异步非阻塞，抛弃 Zuul 的 Servlet 同步 BIO；
架构由 **Route (路由目的地)、Predicate (断言匹配规则)、Filter (前后置加工)** 三组件组成；
请求进来先经过全路由的断言匹配，满足条件进入对应路由，再执行过滤器链，前置处理后负载均衡转发下游服务，
拿到响应后执行后置过滤器返回数据。
up（落地项目解决问题）
项目接入 Gateway，靠 Path/Method 断言区分不同接口，自动分发到用户、订单、代驾各个微服务；
依靠全局过滤器统一实现跨域、接口鉴权、Sentinel 网关限流、黑名单拦截；
不用每个服务单独写鉴权限流代码，依托 Netty 异步架构扛住代驾高峰期高并发，不会像 Zuul 同步模型出现线程池打满宕机问题。

请求进来 → 断言匹配路由 → 路由确定目标微服务 → 过滤器加工请求 → 转发到微服务

前端（网页 / H5 / 小程序） → 访问 后端接口
只要 三个东西有一个不一样，浏览器就会拦截，不让访问，这就叫跨域。
三个不一样是：
域名不一样（a.com → b.com）
端口不一样（8080 → 8600）
协议不一样（http → https）
只要不一样，浏览器默认禁止访问，报红错：
No 'Access-Control-Allow-Origin' header
跨域 = 浏览器的安全限制，不让前端随便访问不同端口 / 不同地址的后端。
网关配置跨域 = 告诉浏览器：允许前端访问后端接口。

二、Feign 怎么传 token？（你项目里一定用到）
微服务之间调用，必须把用户登录的 token带给下游服务，不然下游不知道是谁在调用。
两种最常用方式（你项目用的就是第一种）
1. RequestInterceptor 统一传递（最标准、最常用）
写一个拦截器，从当前请求头里拿到 token，塞到 Feign 发出的请求头里。
```text
@Component
public class FeignTokenInterceptor implements RequestInterceptor {
    @Override
    public void apply(RequestTemplate template) {
        // 1. 从上游请求拿到 token
        ServletRequestAttributes attributes = (ServletRequestAttributes) RequestContextHolder.getRequestAttributes();
        HttpServletRequest request = attributes.getRequest();
        String token = request.getHeader("token");

        // 2. 塞到 Feign 调用的请求头里
        template.header("token", token);
    }
}
```
2. 手动传（不推荐）
在接口方法上加 @RequestHeader。

4  **Sentinel限流/熔断/降级怎么配置、作用？**
一、先记住 3 个核心作用（一句话区分）
限流：控制每秒最多进来多少请求，防止流量太大打崩服务
熔断：下游服务挂了 / 响应慢，直接切断调用，不放请求过去
降级：熔断后，返回一个友好提示 / 默认值，不让系统报错
二、Sentinel 三大功能作用（面试满分版）
1. 限流（Rate Limiter）
控制 QPS，防止流量冲垮服务
比如：设置每秒最多 100 个请求
超过的直接拒绝
保护服务不被打崩
2. 熔断（Circuit Breaker）
下游服务出问题，立刻切断调用
比如：支付服务超时 / 报错率太高
断路器打开，不再调用它
防止雪崩效应（一个服务挂，拖死全部）
3. 降级（Fallback）
熔断 / 限流后，给用户一个兜底结果
不抛 500 错误
返回 “服务繁忙，请稍后再试”
保证系统不崩溃，用户体验好

5  **服务雪崩怎么解决？**
```text
一、先搞懂：什么是服务雪崩
微服务链式调用中，某一个下游服务故障 / 响应缓慢，导致上游请求阻塞、线程耗尽，故障层层向上传导，最终整个系统全部瘫痪，这就是服务雪崩。
举例：前端→网关→乘客服务→订单服务→支付服务
支付服务宕机 / 超时 → 订单服务请求一直等待，线程被占满 → 乘客服务调用也阻塞 → 整条链路全部卡死。
二、主流解决方案（按落地优先级排序，结合你的项目）
1. 熔断（核心方案，Sentinel 实现）
作用：检测到下游服务异常（超时、报错率过高），直接切断调用链路，不再发起请求，避免请求持续堆积。
落地：Feign 整合 Sentinel，触发熔断后跳过远程调用。
特点：主动断联，阻止故障扩散。
2. 降级（配合熔断使用）
作用：熔断 / 调用失败后，执行预设兜底逻辑，返回默认数据、友好提示，不抛异常、不阻塞线程。
落地：Feign 接口指定 fallback 降级类，自定义兜底返回。
3. 限流（网关 / 服务内限流，前置防护）
作用：在请求入口（Gateway 网关）或单个服务内限制请求量（QPS），避免突发大流量压垮服务，从源头减少请求压力。
落地：Sentinel 针对网关、接口配置限流规则，超出阈值直接拒绝请求。
4. 超时控制
作用：给所有远程调用（Feign、HTTP 请求）设置最大超时时间，请求超时就主动终止，不无限占用线程。
落地：配置 Feign、Ribbon 超时参数，避免线程永久阻塞。
5. 线程池隔离
分两类隔离，避免一个服务的请求占满全部线程：
服务隔离：不同微服务使用独立线程池，A 服务故障不会影响 B 服务。
接口隔离：核心接口、非核心接口拆分线程池，保障核心业务可用。
落地：Sentinel 支持线程池隔离，也可手动配置线程池。
6. 集群部署 & 服务冗余
作用：单个服务部署多个实例（集群），一个实例挂了，负载均衡自动切换到其他健康实例，单点故障不影响整体。
落地：你的项目中所有微服务多实例部署，Nacos+Ribbon 实现负载均衡。
7. 异步调用
作用：非核心业务改用异步调用（线程、消息队列 MQ），同步阻塞变少，主线程不会被卡住。
落地：次要接口使用 MQ 解耦、异步处理，切断同步调用链。
三、完整执行链路（串成一条线，面试口述）
请求进入网关 → 网关限流拦截超额流量 → 正常请求进入业务服务
调用下游服务前：设置调用超时，避免线程阻塞；
调用中：通过 Sentinel 做线程隔离；
若下游频繁报错 / 超时：触发熔断，停止调用；
熔断后执行降级兜底逻辑；
同时服务采用多实例集群，规避单点故障；非核心业务使用异步 / MQ解耦。
通过以上组合方案，彻底防止服务雪崩。
四、面试精简背诵版（2 个版本，按需选择）
版本 1（简短版，日常问答）
服务雪崩是下游故障逐级向上扩散导致系统瘫痪。解决主要依靠 Sentinel 实现限流、熔断、降级，同时配置调用超时、线程池隔离；服务做集群部署避免单点故障，非核心业务改用异步或消息队列解耦，多手段结合阻断故障传播。
版本 2（详细版，深度面试）
首先理解服务雪崩是链式调用下故障层层蔓延引发的系统瘫痪。解决方案分为多层防护：
入口层：基于 Gateway + Sentinel 做限流，从源头控制流量；
调用层：给 Feign 远程调用配置超时时间，搭配线程池隔离，避免线程耗尽；
故障防护：利用 Sentinel 实现熔断切断异常调用，配合降级返回兜底数据；
架构层面：微服务多实例集群部署，消除单点问题；非核心业务通过 MQ 异步解耦，斩断同步调用链。
补充区分易混点
限流：防大流量；
熔断：防下游故障扩散；
降级：熔断后的兜底方案；
三者搭配，是应对雪崩最核心的组合。
```

2  **Redis GEO原理、你项目怎么用？**
```text
一、Redis GEO 原理（一句话 + 三层拆解）
一句话：GEO 就是 ZSet + GeoHash，把二维经纬度压成一维分数，实现附近查询。
1. 底层结构：不是新类型，就是 ZSet
key：比如 shops:geo、drivers:geo
member：店铺 ID / 用户 ID / 司机 ID
score：经纬度 → GeoHash → 52 位整数（存到 double 不丢精度）Redis
plaintext
ZSet: shops:geo
  member=shop1  score=123456...(GeoHash)
  member=shop2  score=789012...
2. GeoHash 核心：二维变一维，保留邻近性
把地球切成格子：
经度：[-180,180]
纬度：[-90,90]
交替二分 → 生成二进制 → 转成 52 位整数
优点：相近坐标 → GeoHash 前缀相似 → score 接近
代价：边界格子会有 “邻居断裂”（要查周围 8 格补全）
3. 查询流程（为什么快）
用户坐标 → 算中心 GeoHash
查中心 + 周围 8 格的 score 范围
ZSet 按 score 范围查（O (logN)）
用Haversine 公式算真实距离，过滤掉半径外的点
按距离排序返回
复杂度：O (logN) + 少量距离计算 → 毫秒级
四、面试标准回答（背这个就行）
Redis GEO 是 Redis 3.2 引入的地理空间功能，底层基于 ZSet 实现，利用 GeoHash 算法将二维经纬度编码为 52 位整数作为 ZSet 的 score，member 存业务 ID。
原理核心是把二维坐标降维成一维有序数值，保留空间邻近性，查询时通过中心 + 周围 8 格做范围查询，再用 Haversine 公式精确过滤并排序。
项目中主要用于附近商家、网约车司机匹配、附近的人、配送范围判断等，特点是毫秒级响应、支持实时位置更新、命令简洁。

1. 基础问答（必问）
你们项目用 GEO 做了什么？
答：实现司机实时位置存储、乘客查询附近在线司机、计算里程，支撑代驾就近派单。
Redis GEO 底层是什么结构？
答：基于 ZSet 实现，借助 GeoHash 将二维经纬度转为一维数字作为 score。
2. 实操 & 踩坑（加分项，拉开差距）
司机位置高频更新怎么处理？
司机端轮询上报坐标，GEOADD 覆盖更新；搭配 EXPIRE 做过期淘汰，离线司机自动剔除。
GeoHash 边界问题怎么应对？
邻近区域落在不同网格，会漏查，Redis GEOSEARCH 底层默认检索周边 8 个网格，规避该问题，业务层无需额外处理。
为什么不用数据库存经纬度查询？
数据库经纬度计算、范围查询效率极低，高并发下扛不住；Redis 内存操作，毫秒级响应，适合司机位置这种高读写、实时性要求高的数据。
数据量大了怎么办？
可按区域分片（比如不同城市拆分不同 GEO 的 key），减少单个 ZSet 的数据量，提升查询速度。
3. 原理简述（问到就答）
经纬度通过 GeoHash 算法二分编码，转为 52 位整数作为 ZSet 的 score；坐标相近的点，score 数值也接近，利用 ZSet 有序特性做范围查询，最后再计算真实距离排序。
四、总结 & 学习建议
重要程度判定

你（乐尚代驾项目）：重点掌握，属于项目核心亮点，必须吃透。
背诵精简版（面试直接用）
乐尚代驾项目中，Redis GEO 是就近派单的核心组件。底层基于 ZSet+GeoHash 实现，将司机经纬度编码后存储。

经纬度是二维数据（经度、纬度），没法直接做范围查询。
GeoHash 把 (经度，纬度) 交错二分编码，转成一串二进制，最终转为整数作为 ZSet 的 score：
地理位置越近，GeoHash 编码前缀越相似 → score 数值越接近；
ZSet 天生按 score 排序，能直接做范围区间查询（O (logN) 复杂度）。
2. 和普通 Hash 的本质区别
普通 Hash（HashMap/Redis Hash）：目标是 key 寻址、精准查找，擅长「根据唯一 key 拿数据」，不支持范围查询；
Geo 里的 GeoHash：是坐标编码规则，作用是把二维位置变成可排序的一维数值，配合 ZSet 实现空间范围检索。

英语里 Hash = 打散、混合、映射
HashMap 和 GeoHash 共享同一个底层思想：Hash 映射
只是后面 “怎么用这个数字” 不一样！
HashMap 用数字做 下标、查找
GeoHash 用数字做 编码、排序
```

3  **缓存穿透/击穿/雪崩，你项目怎么做？**
```text
一、先给你3 秒区分口诀（一辈子不混）
穿透：查根本不存在的数据 → 缓存没有，直接打数据库
击穿：一个热点 key 过期 → 大量请求瞬间打数据库
雪崩：大量 key 同时过期 / Redis 挂了 → 全部请求打数据库
二、逐个讲：是什么 + 怎么解决（你的项目怎么用）
1. 缓存穿透
是什么？
用户查 id = -1、id = 9999999 这种根本不存在的数据。
缓存里没有 → 每次都查数据库 → 数据库压力巨大。
项目解决方案（2 个）
空值缓存
查不到数据时，往 Redis 存一个 null 或空对象，设置短暂过期时间（30s～1min）。
下次再查，直接返回空，不进数据库。
布隆过滤器（Bloom Filter）高级版
把所有存在的 ID 提前放进布隆过滤器，请求过来先判断：
不存在 → 直接返回
存在 → 再查缓存
你们项目如果是高并发，一般用这个。
2. 缓存击穿
是什么？
一个超级热点 key（比如首页爆款、热门司机信息）
突然过期了！
一瞬间 10000 个请求同时进数据库 → 库直接崩
项目解决方案（2 个）
互斥锁（mutex lock）
第一个请求去查数据库，其他请求等待，查完放入缓存。
热点 key 永不过期
后台异步定时更新，不让它自动过期。
最常用、最简单、最稳。
3. 缓存雪崩
是什么？
大量 key 同一时间过期
或 Redis 直接挂了
所有请求同时冲进数据库 → 直接雪崩
项目解决方案（4 个，必背）
过期时间加随机值
比如本来 1 小时过期 → 变成 3600 秒 + 随机 100 秒
→ 避免同时过期
多级缓存
Redis + Caffeine（本地缓存）
Redis 挂了，还有本地缓存顶一下。
Redis 集群 / 哨兵模式
主从 + 哨兵，一台挂了自动切换，避免 Redis 单点挂掉。
服务降级、熔断
用 Sentinel 限流、降级，不让请求冲到数据库。
三、面试满分回答（直接背这一段）
缓存穿透、击穿、雪崩是 Redis 高并发下三大问题：
缓存穿透是查询不存在的数据，解决方案是缓存空值和布隆过滤器；
缓存击穿是热点 Key 过期失效，解决方案是互斥锁和热点 Key 永不过期；
缓存雪崩是大量 Key 同时失效或 Redis 宕机，解决方案是过期时间加随机值、Redis 集群高可用、多级缓存以及熔断降级。
```

```text
一、InnoDB 索引结构
InnoDB 主键索引（聚簇索引） 和 二级索引（普通索引） 底层都采用 B+ 树 结构，结合磁盘页管理。
1. B+ 树基础结构
整棵树由 ** 磁盘页（Page）** 组成，一页默认 16KB，是磁盘 IO 最小单位。
非叶子节点：只存索引键 + 子节点指针，不存完整数据，仅用来路由查找。
叶子节点：
存储完整索引数据；
所有叶子节点通过双向链表串联，有序排列；
数据按索引字段排序。
2. 聚簇索引（主键索引）
InnoDB 表数据本身就存在主键索引的叶子节点里，索引和数据融为一体。
叶子节点存放：主键值 + 整行所有字段数据。
一张表有且仅有一个聚簇索引：
显式定义主键 → 主键作为聚簇索引；
无主键 → 选唯一非空索引；
都没有 → 系统自动生成隐藏 rowid 作为聚簇索引。
3. 二级索引（普通 / 唯一 / 联合索引）
叶子节点只存：索引列值 + 主键值，不存整行数据。
查找流程（回表）：
走二级索引找到对应主键；
再用主键去聚簇索引查询整行数据，这个过程叫回表。
补充：覆盖索引
如果查询字段全部在二级索引里，不需要回表，就是覆盖索引，性能最优。
二、B+ 树 对比 B 树 / 哈希表 的核心优势（面试必背 5 点）
磁盘 IO 次数更少，查询效率高
B+ 树非叶子节点不存数据，单页能存放更多索引键，树的高度更低。InnoDB 千万级数据，B+ 树高度一般仅 3~4 层，最多 3~4 次磁盘 IO 就能查到数据。
范围查询、排序、分组极强
叶子节点是有序双向链表，命中起点后，直接顺着链表遍历即可，不用再回溯上层节点。B 树、哈希表做范围查询效率很差。
查询性能稳定
无论等值查询还是范围查询，都要走到叶子节点，所有查询 IO 次数基本一致；哈希表存在哈希冲突，性能波动大。
全表扫描高效
直接遍历叶子链表即可，无需整树遍历，适配数据库遍历场景。
插入、删除更友好
数据集中在叶子节点，非叶子节点变动少，节点分裂 / 合并概率低，维护成本低。
三、精简答题话术（口头回答版，流畅自然）
InnoDB 索引底层使用 B+ 树 结构，默认一页 16KB。
它分为聚簇索引和二级索引：聚簇索引叶子节点存放整行数据，也是表本身；二级索引叶子只存索引列和主键，查询时会根据主键回表拿数据。
B+ 树相比其他结构优势很明显：
第一，非叶子节点只存索引，树高更低，减少磁盘 IO；
第二，叶子节点有序链表，范围查询、排序非常快；
第三，查询性能稳定，也适合全表遍历，增删维护成本也更低。
四、高频连环追问（提前准备）
为什么不用 B 树？
B 树每个节点都存数据，单页索引数量少，树更高、IO 更多；且范围查询需要跨节点跳转，效率不如 B + 树链表遍历。
为什么不用哈希索引？
哈希只适合等值查询，不支持范围、排序、联合索引最左匹配；存在哈希冲突，且数据无序。
聚簇索引为什么建议用自增主键？
自增主键有序，插入数据时 B+ 树叶子节点追加写入，不会触发节点分裂，减少页分裂开销；无序主键会频繁分裂页，影响性能。
联合索引最左匹配原则怎么理解？
B+ 树索引按索引字段顺序排序，必须先匹配最左前列，才能继续向后匹配。
```

4  **MySQL事务隔离级别、默认、脏读/不可重复读/幻读？**
```text
** 不可重复读 = 行内容变了（修改 / 删除）; 幻读 = 行数量变了（新增）**
行 = 数据库表里的一行数据（记录）

幻读 Phantom Read
Phantom 本意是幻影、幽灵。
直译：读到了幽灵一样的数据。
聚焦现象：凭空多出 / 少了行，像幻觉一样。
强调：之前查询不存在的记录，突然冒出来，仿佛是幻象。

三、问题 3：MySQL 可重复读（RR）底层原理（核心：MVCC + 锁机制，逐条拆解）
MySQL InnoDB 默认隔离级别是可重复读，依靠两大核心实现：MVCC（多版本并发控制） 解决脏读、不可重复读；临键锁 + 间隙锁 解决幻读。下面分模块串完整流程。
前置基础：InnoDB 隐藏字段
每一行记录自带 3 个隐藏列，是 MVCC 的基石：
DB_TRX_ID：最后修改这条数据的事务 ID；
DB_ROLL_PTR：回滚指针，指向undo log（回滚日志） 里的旧版本数据；
DB_ROW_ID：行 ID，无主键时用作聚簇索引。
一、MVCC 多版本并发控制（解决脏读、不可重复读）
核心思想：同一行数据保留多个历史版本，不同事务读不同版本，读写不阻塞。
分为快照读和当前读两种读取方式。
1. 快照读（普通 SELECT，不加锁，主流查询）
执行普通 select * from table 时触发，逻辑：
事务开启时，生成一个一致性视图（由当前活跃事务 ID 列表、最小 / 最大事务 ID 组成）；
读取数据时，根据视图规则判断：只读取当前事务开启前已提交的数据，看不到其他事务未提交、事务开启后新修改的数据；
如果当前**行**版本不符合规则，就通过roll_ptr顺着 undo log 找历史版本，直到找到符合条件的版本返回。
👉 效果：
看不到未提交数据 → 解决脏读；
同一个事务全程用同一份一致性视图，两次查询拿到同一个版本数据 → 解决不可重复读。
2. 当前读（加锁查询 / 写操作，会阻塞）
执行 select ... for update、update、delete、insert 时触发，读取最新数据，并且加锁防止其他事务修改。
二、锁机制（临键锁 + 间隙锁，解决幻读）
单纯 MVCC 无法彻底杜绝幻读（特定场景下仍能读到新插入数据），所以 RR 级别搭配锁体系：
行锁：锁定已存在的记录，防止其他事务修改 / 删除；
临键锁：InnoDB RR 默认锁，是「行锁 + 间隙锁」的结合，锁定某一条记录 + 记录左右的间隙；
    它锁住两样东西：
    行本身（不让改 / 删）
    行与行之间的空隙（不让插）
    所以临键锁的作用是：
    既不让你改这一行，也不让你在这一行附近插入新行！
间隙锁：专门锁定两条数据之间的 “空白区间”，禁止其他事务在间隙内插入新数据。
👉 效果：间隙锁住数据空隙，新行无法插入，同一个事务两次查询的行数不会变化 → 解决幻读。
三、整体运行流程（串联背诵版）
开启事务，生成一致性视图；
普通查询走快照读，依靠视图 + undo log 读取历史版本，杜绝脏读、不可重复读；
增删改、加锁查询走当前读，配合临键锁 / 间隙锁锁定数据与数据间隙，阻止新数据插入，解决幻读；
事务提交后，根据事务 ID 更新数据版本，旧版本逐步清理。
补充高频考点 & 易错点
undo log 作用：保存数据历史版本，支撑 MVCC 版本回溯，同时用于事务回滚；
RR 和 RC（读已提交）MVCC 区别：
RC：每次查询都会重新生成视图，所以会出现不可重复读；
RR：一个事务内只生成一次视图，保证两次读取版本一致；
间隙锁副作用：会带来锁等待、死锁风险，这是 RR 级别不可避免的代价。
整合面试完整版回答（直接背诵）
MySQL 可重复读是默认隔离级别，底层依靠 MVCC 多版本并发控制 + 临键锁 / 间隙锁 共同实现。
首先 MVCC 依托每行数据的隐藏事务 ID、回滚指针和 undo log，为数据保存多个版本。
普通查询走快照读，事务开启时生成一致性视图，整个事务内视图不变，只能读取事务开启前已提交的数据，以此解决脏读和不可重复读。
对于更新、删除、加锁查询这类当前读，InnoDB 会使用临键锁和间隙锁，不仅锁定已有数据行，还会锁定数据之间的间隙，禁止其他事务插入新数据，从而解决幻读问题。

快照量级：不是整张表，是行级多版本 + 轻量 ReadView，只存修改行的历史版本，空间很小。
提交对比范围：只对比当前事务修改过的行，不是整张表；检查这些行是否被其他事务改动。
提交失败概率：普通场景很低，因为是行级锁，只在 ** 同一行并发修改（热点行）** 时冲突才高。
```

```text
业界会按粒度、范围、姿态、兼容性、场景多维度划分，不用死记硬背所有分类，重点记面试高频分类即可，分类之间相互交叉。
常用分类（精简版，按学习优先级排序）
按锁定粒度（范围大小）
表锁：锁住整张表，粒度大、并发低、实现简单；
行锁：只锁单行数据，粒度小、并发高，MySQL InnoDB 主力；

按读写兼容性（互斥关系）
共享锁（S 锁 / 读锁）：加锁后，其他人可以读、不能写；
排他锁（X 锁 / 写锁）：加锁后，其他人读写都禁止。
按实现思想
悲观锁：默认会冲突，先加锁再执行；

MySQL 专属锁（事务场景必考）
行锁、间隙锁、临键锁、意向锁、元数据锁（MDL）。

悲观锁

读写锁：读共享、写互斥（ReentrantReadWriteLock，单机）

自旋锁：抢不到锁不阻塞，循环重试（CAS 底层）
```

**JVM**
```text
一、JVM 内存结构（运行时数据区）
核心前提
JVM 启动后，会划分出运行时数据区，线程分为线程私有和线程共享两大类，这是面试第一问必区分的点。
线程私有：线程之间互不干扰，线程销毁，内存随之释放
线程共享：全局共用，整个 JVM 生命周期存在
1. 五大运行时数据区（标准划分）
（1）程序计数器（PC 寄存器）【线程私有】
作用：记录当前线程执行到哪一行字节码指令，线程切换后恢复执行位置。
特点：
JVM 中唯一不会发生 OOM（内存溢出） 的区域；
空间极小，只存指令地址。
面试补充：解释多线程切换靠它记录位置。
（2）虚拟机栈（Java 栈）【线程私有】
作用：执行普通 Java 方法，存放栈帧。
栈帧包含：局部变量表、操作数栈、动态链接、方法出口等。
生命周期：调用方法 → 入栈；方法执行完毕 → 出栈。
两种异常（高频考点）：
StackOverflowError：栈深度过大（如无限递归）；
OutOfMemoryError：虚拟机栈可动态扩展，内存不足（少见）。
（3）本地方法栈【线程私有】
承接你上一问的本地方法：
作用：专门执行 native 本地方法（C/C++ 实现）；
异常类型和虚拟机栈一致：栈溢出、内存溢出。
（4）堆（Heap）【线程共享】
⭐ JVM 最核心区域，面试重中之重
作用：存放所有对象实例、数组，几乎所有 new 出来的东西都在堆中。
特点：
整个 JVM 最大内存区域；
垃圾回收（GC）的主要场所；
会发生 OOM（对象太多，内存占满）。
堆分区（主流分代模型，必背）：
新生代（Young）：存放新建对象，GC 频繁
Eden 区（伊甸区）：大部分对象诞生地
两个 Survivor 区（幸存区）：From / To，大小默认 1:1
老年代（Old）：存放存活很久的对象、大对象
口诀：新对象放 Eden，活下来进 Survivor，熬过多次 GC 升入老年代。
（5）方法区（Method Area）【线程共享】
JDK 版本有差异，面试必问版本区别！
作用：存放类元数据：类结构、常量、静态变量、即时编译代码、运行时常量池。
版本演变（高频）：
JDK 8 之前：方法区 = 永久代（PermGen），使用堆内存，易 OOM；
JDK 8 及以后：彻底移除永久代，改用元空间（Metaspace），直接使用本地物理内存，基本不会溢出。
补充：运行时常量池、字符串常量池现在也逐步调整位置。
2. 内存区速记 + 面试问答精简版
线程私有：程序计数器、虚拟机栈、本地方法栈
线程共享：堆、方法区（元空间）
唯一不 OOM：程序计数器
GC 主战场：堆
本地方法栈：专门执行 native 方法

1. 整体流程
类从 .class 字节码文件加载到 JVM 内存，并转为可使用的 Class 对象，全程分为 5 个阶段（顺序固定）：
加载 → 验证 → 准备 → 解析 → 初始化
阶段 1：加载（Loading）

读取字节码到内存；

通过数组定义类引用
引用父类，只初始化子类
2. 类加载器（ClassLoader）
1）四层双亲委派模型（面试核心）
层级从上到下：
启动类加载器 (Bootstrap) → 扩展类加载器 (Extension) → 应用类加载器 (App) → 自定义类加载器
2）双亲委派规则（一句话背）
加载类时，先向上委托父加载器；父加载器无法加载，自己才加载。
流程：
自定义加载器 → 委托应用加载器
应用 → 委托扩展
扩展 → 委托启动类加载器（顶层，C++ 实现）

安全：防止核心类被篡改（比如自定义 java.lang.String 不会被加载）；

4）补充
启动类加载器：加载 JDK 核心类（java.lang.*）；
应用类加载器：加载我们自己写的代码、第三方 Jar 包（日常项目 99% 都是它）。
类加载极简背诵版
类加载分五步：加载、验证、准备、解析、初始化；
准备阶段赋默认值，初始化才赋代码值；
触发初始化有 6 种主动场景；
类加载器采用双亲委派，向上委托，保证安全和类唯一性。
三、垃圾回收（GC）机制【面试最高频，分模块精讲】
前置基础
GC 目标：回收堆内存中不再被使用的对象，释放空间；
判断前提：怎么确定对象 “死亡”（不能再被使用）
（一）对象存活判断
1. 引用计数法（已淘汰）
原理：对象被引用 + 1，引用消失 - 1；计数 = 0 判定为垃圾。
致命缺点：无法解决循环引用（两个对象互相引用，计数永远不为 0），JVM 堆不再使用。
2. 可达性分析算法（JVM 现在主流，必背）
核心思路：
定义一系列 GC Roots（根对象），从根对象向下遍历引用链；
遍历不到的对象 = 垃圾对象，可回收。
哪些可以作为 GC Roots？（面试常考）
虚拟机栈中引用的对象（局部变量）
本地方法栈中引用的对象
方法区中静态变量、常量引用的对象
活跃线程对象
补充：循环引用问题
可达性分析完美解决循环引用，这是 JVM 选择它的核心原因。
（二）对象的四种引用（面试高频）
从强到弱排序，不同引用回收规则不同：
强引用（默认）
普通赋值 Object obj = new Object();
永远不会被 GC 回收，直到引用断开。
软引用 SoftReference
内存充足：不回收；内存即将溢出：一定会回收。
用途：缓存（Redis 之外的本地缓存兜底）。
弱引用 WeakReference
只要触发 GC，不管内存够不够，直接回收。
用途：防内存泄漏，如 ThreadLocal。
虚引用 PhantomReference
最弱引用，无法获取对象，仅用来跟踪 GC 回收动作，几乎不用。
（三）分代收集理论（堆分代的原因）
现实规律：
大部分对象朝生夕死（新生代，很快被回收）；
少数对象存活时间极长（老年代）。
所以 JVM 堆分新生代、老年代，不同区域用不同 GC 算法，提升效率。
（四）三大垃圾回收算法（原理 + 优缺点）
1. 标记 - 清除（Mark-Sweep）
流程：标记垃圾 → 统一清除垃圾
缺点：产生大量内存碎片，大对象无法分配。
2. 复制（Copy）【新生代主流】
流程：把存活对象复制到另一块空白内存，原区域整体清空。
新生代 Eden + 两个 Survivor 就是这套算法。
优点：无碎片、效率高；
缺点：需要预留一块对等内存，占用空间。
3. 标记 - 整理（Mark-Compact）【老年代主流】
流程：标记垃圾 → 存活对象向一端移动，压缩内存 → 清除边界外垃圾。
优点：无内存碎片；
缺点：移动对象，开销比复制算法大。
总结搭配：
新生代 → 复制算法；
老年代 → 标记 - 清除 / 标记 - 整理。
（五）新生代 GC & 老年代 GC 名称
Minor GC（轻 GC）：新生代垃圾回收
触发频繁，速度快；
Eden 区满就触发，存活对象移入 Survivor 区。
Major GC / Full GC（全量 GC）：老年代回收
触发少，速度极慢（STW 时间长）；
触发场景：老年代空间不足、显式调用 System.gc()、MinorGC 后晋升对象过多等；
面试重点：线上尽量避免 Full GC，是性能杀手。
补充：STW（Stop-The-World）【必问】
含义：GC 执行时，所有用户业务线程全部暂停，只让 GC 线程工作；
原因：防止对象引用状态不断变化，保证回收准确性；
痛点：STW 时间越长，接口卡顿越严重，调优核心就是降低 STW 时长。
（六）常见垃圾收集器（面试区分主流，初级不用深挖源码）
按使用场景划分，只记企业主流款：
Parallel Scavenge + Parallel Old（JDK8 默认组合）
并行收集器，侧重吞吐量（运行代码时间 / 总时间），普通业务项目最常用。
G1（Garbage-First）（JDK9 + 默认，现在主流）
分区收集，兼顾吞吐量和低延迟（减少 STW）；
适合大内存、低延迟需求项目。
其他：CMS（并发低延迟，JDK14 已废弃）、ZGC（超低延迟，高版本 JDK）了解即可。
（七）常见内存溢出 OOM 原因（结合项目面试题）
面试常结合你的代驾项目提问，常见场景：
堆 OOM：创建过多大对象、集合无限扩容、内存泄漏；
虚拟机栈 OOM：无限递归；
元空间 OOM：动态加载大量类、动态生成 Class。
四、JVM 综合面试高频补充（整合易混题 + 标准回答）
1. 经典问答（直接背诵）
1）JDK7 和 JDK8 方法区区别？
JDK7：方法区 = 永久代，堆内存，易 OOM；
JDK8：移除永久代，改为元空间，使用本地内存，基本不会溢出。
2）可达性分析的 GC Roots 有哪些？
虚拟机栈、本地方法栈引用对象；方法区静态 / 常量引用对象；活跃线程。
3）Minor GC 和 Full GC 区别？
Minor GC：回收新生代，频率高、速度快、STW 短；
Full GC：回收整堆 + 方法区，频率低、速度极慢，线上尽量避免。
4）四种引用使用场景？
强引用：常规对象；
软引用：本地缓存；
弱引用：防内存泄漏；
虚引用：跟踪回收。
5）双亲委派模型好处？
防止 JDK 核心类被篡改，保证类只加载一次。
2. 结合你项目的提问预判（面试官大概率会问）
你们项目有没有遇到 OOM？怎么排查？
回答思路：先用 jmap 导出堆快照 → 分析大对象 / 泄漏对象 → 定位代码（集合未清理、局部对象过多）。
为什么新生代用复制算法，老年代不用？
新生代对象存活率极低，复制成本小；老年代对象存活率高，复制开销大，改用标记整理防碎片。
Full GC 频繁怎么排查优化？
排查大对象、内存泄漏、不合理晋升，优化堆参数，减少 Full GC 触发。
3. 极简整体背诵串讲（口述版，面试 1 分钟说完）
JVM 运行时数据区分线程私有和共享：
私有区包括程序计数器、虚拟机栈、本地方法栈，计数器唯一不 OOM；
共享区是堆和方法区，堆是 GC 主战场，JDK8 后方法区改为元空间。
类加载分为加载、验证、准备、解析、初始化五步，准备赋默认值，初始化执行静态代码；
类加载器使用双亲委派，向上委托保证安全。
垃圾回收用可达性分析判断垃圾，分代收集：
新生代用复制算法，发生 Minor GC；老年代用标记整理，发生 Full GC；
GC 都会产生 STW，项目中重点优化 STW 和避免频繁 Full GC。
```

```text
全链路三层防护：生产者用发布确认保证投递可靠；MQ 开启持久化；消费者手动 ACK，业务成功再签收，异常消息重回队列，彻底防止消息丢失。
2. 如何保证消息不重复消费（幂等）
整套是四层兜底，层层拦截，从请求入口到数据库最终防护，结合两端代码逐一说明：
第一层：Redis 抢单标识（生产者前置拦截）
抢单前通过 Lua 原子脚本判断订单可抢标识，抢单成功后立即删除标识；重复请求直接拦截，无法进入发消息逻辑。
第二层：Redisson 分布式锁（并发互斥）
tryLock(0, ...) 非阻塞抢锁，同一订单同一时间只允许一个线程执行业务，并发请求直接失败。
第三层：MySQL 订单状态机
更新条件强制 eq(OrderInfo::getStatus, OrderStatus.WAITING_ACCEPT)
订单一旦被接单，状态变为 ACCEPTED，后续重复消息查询不到对应状态，更新直接失败。
第四层：MySQL 乐观锁（最终兜底，本段代码核心）
更新条件携带 eq(OrderInfo::getVersion, 旧版本)，更新时版本号 + 1；
只要有一条消息执行成功，版本号发生变化，后续重复消息因为版本不匹配，rows != 1，直接判定抢单失败。
面试精简版：
我们采用四层幂等方案：Redis 标识、分布式锁做前置拦截；数据库状态机 + 版本乐观锁做最终兜底。即使 MQ 重复推送，也无法修改数据，保证不会重复抢单、产生脏数据。

项目没有单独建消息去重表，复用现有业务字段做幂等，高并发下性能更高，减少额外库表压力。

业务层面（核心）
本抢单场景中，一个订单只会产生一条 MQ 消息，不存在同一个订单多条消息的顺序问题，从业务根源杜绝乱序。
拓展追问（面试官常考）
如果后续业务拓展，同一个订单需要多条顺序消息（如下单→支付→完结）：
生产者保证单线程发送；

面试精简版：
当前场景单个订单仅生成一条消息，无顺序困扰；若未来需要顺序消息，会使用单生产者 + 单消费者模式，依靠队列特性保证有序。

1. 手动 ACK 相关方法区别
① channel.basicAck(deliveryTag, false)
作用：正常消费成功，确认签收；

场景：订单已被删除、数据不存在；
处理：直接 ack 签收，不再重试；

问题 1：basicNack(..., true) 无限重试风险
当前异常消息会无限重回队列，如果是代码 BUG、数据永久异常，消息会死循环重试，占用队列资源。
✅ 优化方案：
配置 死信队列 (DLQ)；
设置消息最大重试次数（如 3~5 次）；
超过重试次数后，不再重回队列，转发到死信队列，人工排查。
问题 2：重试风暴风险
大量消息同时异常，反复重试会瞬间压垮数据库。
✅ 优化：
设置 消息重试间隔，或使用延迟队列，避免集中重试。
问题 3：查询仅查 id + version，看似合理，但可进一步优化
当前只查版本，满足乐观锁需求，写法没问题；
进阶优化：结合索引，id 为主键索引，查询性能本身很高，无需改动。
问题 4：没有消息幂等兜底（仅靠数据库）
当前依赖数据库乐观锁 + 状态机，极端场景下可补充：
基于 message.getMessageId() 做全局唯一去重（可选，高并发非必需）。
五、高频连环问答（直接背答案）
1. 问：自动 ACK 和手动 ACK 区别，为什么项目选择手动？
答：
自动 ACK 是消息推送给消费者就立即签收，若此时服务宕机、业务未执行，消息直接丢失；
手动 ACK 把签收权限交给业务，业务执行成功再签收，异常则重试，是保证消息不丢失的标准方案。
2. 问：basicNack 第三个参数 true/false 区别？
答：
true：消息重新放回原队列重试；
false：直接丢弃消息（或转发死信）。本项目异常时需要重试，所以传 true。
3. 问：为什么订单不存在时直接 ack，不重试？
答：
订单已删除，重试没有业务意义，一直重试会浪费 MQ 和数据库资源，因此直接确认消费结束。
4. 问：乐观锁在这里起到什么作用？
答：
作为最终幂等兜底，保证同一条消息只会成功更新一次，重复消费时版本不匹配，更新行数为 0，拦截重复抢单。
5. 问：现在消息会无限重试，你怎么解决？
答：
引入死信队列，配置最大重试次数，重试多次仍失败的消息转入死信队列，人工排查，避免无限循环。
6. 问：为什么不用 basicReject？
答：
basicReject 无法让消息重回队列，本场景需要异常重试，因此使用 basicNack。
```

**RabbitMQ底层原理**
```text
前置说明
RabbitMQ 基于 AMQP 协议 开发，使用 Erlang 语言编写，天生高并发、高可用、支持集群。
下面分「核心组件 → 消息流转原理 → 可靠性原理 → 集群模式」四大模块，都是面试高频考点。
1. 五大核心组件（必背）
生产者（Producer）:发送消息的应用，也就是我们项目中的抢单接口。
交换机（Exchange）:接收生产者消息，根据路由规则转发到对应队列。
常用类型：
Direct（直连）：一对一，精准路由（我们项目使用类型）
Topic（主题）：通配符路由，多用于订阅
Fanout（广播）：一对多，群发消息
队列（Queue）:存储消息的容器，消息最终落地在这里；支持持久化，是消息真正存放的地方。
消费者（Consumer）:监听队列、拉取并处理消息，即我们的 OrderRobConsumer。
虚拟主机（Virtual Host）:类似 MySQL 的数据库，一台 MQ 服务划分多个虚拟主机，隔离不同业务队列。
组件流转关系（一句话）:生产者 → 交换机（路由） → 队列（存储） → 消费者（消费）
2. 消息投递完整原理（底层流转）
生产者与 RabbitMQ 服务端建立 TCP 连接，创建信道（Channel）；
补充：信道复用 TCP 连接，一条连接可开多个信道，减少开销，项目中默认使用。
生产者通过信道发送消息，携带 交换机名称、路由键；
交换机根据类型 + 路由键，匹配绑定的队列，将消息投递进去；
消息进入队列排队，持久化后的消息会写入磁盘；
消费者监听队列，建立信道拉取消息，执行业务逻辑。
3. 三大可靠性实现原理（对应你的代码，重中之重）
对应前面 “不丢、不重、不乱序”，结合底层原理讲解：
（1）消息不丢失 三层原理
生产者可靠性（发布确认 Publisher Confirm）
生产者发送消息后，MQ 服务端会返回 ACK/NACK 回执。
原理：消息成功写入队列持久化后才返回确认，失败则通知生产者，生产者可重试。
对应代码：CorrelationData 实现同步等待回执。
服务端可靠性（持久化）
交换机持久化：重启后交换机配置不丢失；
队列持久化：队列本身不被删除；
消息持久化：消息写入磁盘，而非仅存内存。
原理：内存 + 磁盘双存，宕机重启从磁盘恢复数据。
消费者可靠性（手动 ACK）
原理：MQ 推送消息后，不会立刻删除；必须收到消费者的 basicAck 确认，才会移除消息。
消费异常调用 basicNack，消息重新入队。
自动 ACK 则推送即删除，极易丢消息。
（2）消息不重复（幂等原理）
MQ 重复消息根源：网络抖动、重试、节点切换。
底层无法彻底杜绝重复，所以业务层做幂等：
原理：利用唯一标识、状态判断、乐观锁，保证同一条消息多次执行，结果一致。
对应项目：Redis 标识、分布式锁、数据库状态 + 版本号。
（3）消息不乱序原理
RabbitMQ 单个队列内部默认 FIFO 先进先出。
原理：
单队列 + 单消费者：严格保证顺序；
多消费者 / 多队列会打乱顺序。
我们项目单订单仅一条消息，天然无顺序问题。
4. 高级补充（面试加分，中小厂常问）
（1）信道（Channel）和连接（Connection）区别
Connection：客户端与 MQ 的 TCP 物理连接，创建开销大；
Channel：连接内的逻辑信道，轻量级，一个连接可创建多个信道，业务都使用信道通信。
（2）死信队列（DLQ）原理
普通队列中消息满足：超时、被拒绝、达到最大重试次数 → 自动转发到死信队列。
用途：处理异常消息，避免无限重试，是项目优化方向。
（3）集群模式（简单了解）
普通集群：节点共享队列数据，无数据同步；
镜像集群：队列镜像到多个节点，主节点宕机，从节点接管，实现高可用。
原理部分精简背诵版（面试通用）
RabbitMQ 基于 AMQP 协议、Erlang 语言开发，核心组件包含生产者、交换机、队列、消费者。
消息流转：生产者通过信道发送消息，由交换机按路由规则分发到队列，消费者监听消费。
为保证可靠性：生产者开启发布确认，服务端开启三重持久化，消费者使用手动 ACK。
队列默认先进先出，配合业务幂等方案，实现消息不丢失、不重复、不乱序。
常用交换机有直连、主题、广播三种，项目中使用直连模式。
```

3  **你项目抢单发MQ，为什么异步？**
```text
一、Confirm 发布确认 + ACK 消费确认 机制
先分清两个机制所属环节：
Confirm（发布确认）：生产者 → RabbitMQ 服务端，保障发送阶段消息可靠
ACK（消费确认）：RabbitMQ 服务端 → 消费者，保障消费阶段消息可靠

生产者发送消息到 RabbitMQ 服务端；
RabbitMQ 服务端把消息成功写入队列（并持久化到磁盘）后，主动向生产者发送 ACK 回执；
生产者收到 ACK，才会认为消息发送成功；如果收到 NACK 或超时，会认为发送失败，可选择重试。
✅ 你的理解是对的：Confirm 是服务端给生产者的确认，用来保证 “消息确实安全到达了 MQ”。
注意：这里的 ACK/NACK 是服务端发给生产者的回执，不是消费者发的。

RabbitMQ 服务端把消息推送给消费者；
消费者执行业务逻辑，成功后主动向 RabbitMQ 服务端发送 basicAck 指令；
RabbitMQ 收到 ACK，才会把消息从队列中删除；
如果消费失败，消费者发送 basicNack，服务端会把消息重新放回队列重试。

（一）Confirm 发布确认（生产者端，对应你 robNewOrder 代码）
1. 作用
解决网络波动、MQ 宕机导致生产者以为发送成功，实际消息丢失的问题，让生产者明确知道消息是否真正存入队列。
2. 实现方式（项目采用同步确认）
开启 MQ 配置：spring.rabbitmq.publisher-confirm-type=correlated
每条消息绑定唯一 CorrelationData（UUID 作为标识）；
发送消息后同步等待 MQ 回执：
收到 ACK：消息已成功持久化到队列，继续执行业务（删除 Redis 抢单标识）；
收到 NACK / 等待超时：消息发送失败，抛出异常，保留 Redis 标识，允许后续重试。
3. 两种确认模式（补充知识点）
同步确认（你项目使用）：发送后阻塞等待回执，可靠性高，适合抢单这类核心业务；
异步回调：不阻塞，通过回调函数处理结果，吞吐更高，适合海量非核心消息。
面试精简回答
Confirm 是生产者侧的发布确认机制。我们项目开启该配置，每条消息绑定唯一 ID，发送后同步等待 MQ 回执。收到 ACK 代表消息安全入队，才删除抢单标识；NACK 或超时则判定发送失败，保留标识等待重试，避免发送阶段消息丢失。
（二）ACK 消费确认（消费者端，对应 OrderRobConsumer 代码）
1. 两种模式对比（必考点）
自动 ACK（默认）
MQ 把消息推送给消费者，瞬间自动标记消费完成并删除消息。
隐患：消费者服务宕机、代码报错，业务没执行，但消息已丢失。
手动 ACK（项目使用）
关闭自动签收，签收权限交给业务代码：
basicAck(deliveryTag, false)：业务执行成功，正式签收，MQ 删除消息；
basicNack(deliveryTag, false, true)：消费异常，拒绝签收，消息重回队列重试；
basicReject：拒绝消息，不可重试。
2. 代码对应逻辑
订单不存在：直接 ack，无效消息不再重试；
正常更新订单：ack 正常结束；
代码 / 数据库异常：nack 消息重回队列。
面试精简回答
ACK 是消费端确认机制，我们关闭了自动签收，使用手动 ACK。业务正常完成则手动确认，消息被 MQ 移除；消费异常则调用 NACK 让消息重回队列重试，彻底避免消费阶段消息丢失。
（三）组合总结（Confirm + ACK 联用）
Confirm 保证发得出去，ACK 保证消费得掉，配合交换机 / 队列 / 消息三重持久化，构成 RabbitMQ 完整消息可靠性方案。
二、死信队列（DLQ）
1. 基础概念
死信：无法被正常消费的消息。
死信队列：专门接收死信的备用队列，普通队列满足特定条件后，消息会自动转发到死信队列，不再原地无限重试。
2. 消息成为死信的 3 个条件（必背）
消息被 basicNack/basicReject 拒绝，且不重回原队列；
消息在队列中超时（超过设置的 TTL 存活时间）；
普通队列达到最大长度，消息溢出。
3. 结合你项目的痛点 & 解决方案
现有问题
当前消费者异常时执行 basicNack(...,true)，消息会无限循环重试。
如果是代码 BUG、数据异常，消息会一直占用队列、消耗资源，甚至引发重试风暴。
引入死信队列的改造方案（面试加分，讲优化思路）
配置绑定关系
给业务队列绑定死信交换机、死信队列，设置最大重试次数（如 3 次）；
重试规则
消息前 3 次异常，正常重回原队列重试；
超过最大次数 → 自动转发到死信队列，停止重试；
后续处理
运维 / 开发监听死信队列，排查异常数据、修复代码，人工处理消息。
4. 死信队列使用场景
限制消息重试次数，避免死循环；
处理过期订单、超时任务；
异常消息隔离，不影响主业务队列。
面试精简回答
死信队列用于存放无法正常消费的消息。当消息重试超限、超时或被拒绝时，会自动转入死信队列。我们项目目前存在消息无限重试的问题，后续计划接入死信队列，设置最大重试次数，超限消息转入死信人工排查，防止队列阻塞和重试风暴。
三、抢单场景为什么要用异步 MQ（核心问题，高频必问）
结合业务场景、并发压力、架构设计分维度讲解，分精简版（口述）、完整版（深挖），同时对比本地异步（线程池 / CompletableFuture）。
核心结论
抢单是瞬时高并发热点场景，使用 RabbitMQ 异步，核心目的：削峰填、解耦、容错、流量隔离。
1. 削峰填谷（最核心原因）
代驾抢单会出现瞬时海量司机同时请求，同步接口会直接把压力传导到 MySQL：
同步方案：请求 → 直接操作数据库，瞬时高并发压垮 DB，出现超时、锁等待、服务不可用；
MQ 异步：请求先落在 MQ 队列中排队，削平流量峰值，消费者匀速消费，数据库压力平稳。
简单理解：高峰期洪水（请求）先流入水库（MQ），再匀速放水（消费），不会冲垮下游。
2. 业务解耦
同步模式：抢单接口 = 数据库更新逻辑耦合在一起，代码臃肿，一处故障全链路受影响；
异步拆分：
生产者：只做抢单校验、发消息，接口响应极快；
消费者：独立负责数据库更新；
两端独立部署、独立扩容，一方出问题不直接影响另一方。
3. 提升接口响应速度 & 用户体验
同步需要等待数据库 IO、事务执行，接口耗时高；
异步模式：发送消息 + 等待 MQ 回执即可返回结果，接口毫秒级返回，司机端不会长时间等待，体验更好。
4. 容错 & 故障隔离
数据库短暂卡顿、服务抖动：同步接口直接报错；
MQ 异步：消息持久化，下游故障时消息暂存队列，恢复后继续消费，请求不会丢失。
5. 对比：为什么不用线程池 / CompletableFuture 本地异步？
很多面试官会追加这个问题，重点区分：
本地异步（线程池）：和业务服务同进程，流量过大直接打满线程池，触发拒绝策略，无法跨服务容错；
MQ 是独立中间件，集群部署、持久化，独立承载流量，支持横向扩容，高并发稳定性强得多；
本地异步无统一重试、死信等能力，异常处理简陋。
面试分版本回答
版本 1（简短版，日常问答，直接背）

第一，削峰填谷，瞬时请求先进入队列排队，匀速消费，保护 MySQL 不被压垮；
第二，业务解耦，抢单校验和数据库更新拆分，模块独立；
第三，提升接口响应速度，优化用户体验；

版本 2（完整版，深挖面试）
我们抢单接口并发量极高，如果采用同步调用，海量请求会直接冲击数据库，极易造成数据库压力过大、接口超时。
引入 RabbitMQ 做异步处理：
削峰：利用队列缓冲瞬时高并发，将突发流量转为平稳流量，保护核心数据库；
解耦：将抢单前置校验和订单数据库更新拆分为两个独立环节，各司其职，故障互不影响；

四、高频连环追问（配套应答）
追问 1：Confirm 和 ACK 区别？
答：Confirm 是生产者与 MQ之间的确认，保证消息成功发送入队；ACK 是MQ 与消费者之间的确认，保证消息正常消费。二者配合实现全链路消息可靠。
追问 2：手动 ACK 三种方法区别（ack/nack/reject）？
basicAck：正常消费，删除消息；
basicNack：拒绝消费，可重回队列重试（项目使用）；
basicReject：拒绝消费，不可重试，一般配合死信使用。

答：依靠 MQ 可靠性机制 + 数据库乐观锁 / 状态机，消息最终一定会被消费；同时搭配定时巡检任务，核对 Redis 标识与数据库数据，修复不一致脏数据。
追问 5：异步会不会出现数据延迟？怎么处理？
答：会有毫秒～秒级正常延迟，抢单场景可接受；如果对实时性要求极高的业务，会改用同步模式。
```

```text
2. 三者底层原理差异（面试高频）
（1）RabbitMQ 底层原理
架构：基于 Erlang 实现，采用 Exchange-Queue 模型
核心：
消息先发到 Exchange，根据路由规则投递到 Queue
Queue 是消息的最终存储位置，支持持久化
消费时支持手动 / 自动 ACK，异常消息可进入死信队列
特点：路由能力强，可靠性高，但 Erlang 语言本身限制了单节点吞吐量上限。
（2）RocketMQ 底层原理
架构：基于 Java 实现，主从架构（NameServer + Broker）
核心：
所有消息统一写入 CommitLog（顺序写盘），保证高吞吐
CommitLog 异步构建 ConsumeQueue 索引，消费者拉取时通过索引定位消息
支持事务消息、顺序消息、重试队列、死信队列
特点：高吞吐 + 高可靠 + 丰富的业务特性，是国内电商 / 金融常用方案。
（3）Kafka 底层原理
架构：基于 Scala/Java 实现，分布式流平台，分区 + 副本模型
核心：
Topic 分为多个 Partition，每个 Partition 是一个顺序写入的日志文件
生产者按负载均衡写入不同 Partition，消费者按 Offset 拉取
消息默认不删除，按时间 / 日志大小清理，靠副本保证高可用
特点：极致高吞吐，适合日志、事件流，但不适合复杂业务消息场景。
3. 结合你当前项目，为什么选 RabbitMQ？
你的抢单业务核心需求：
异步解耦 + 削峰
死信队列 + 定时任务兜底重试
消息可靠性优先，吞吐不是瓶颈
RabbitMQ 天然支持死信队列、手动 ACK、队列持久化，和你的业务需求完全匹配，开发成本最低。
```

```text
核心原因：业务场景决定「零等待」
1. 抢单是瞬时竞争场景，排队等待无意义
多个司机同时抢同一个订单，本质是 “先到先得”：
已有司机拿到锁，说明订单正在被处理，大概率已经被抢走；

抢单属于高并发接口，瞬时流量大：
若允许锁等待，大量请求阻塞堆积，会导致线程耗尽、接口超时；
0 等待快速失败，请求快速收尾，服务线程可以立刻处理其他订单的抢单请求，整体并发能力更高。

此时再让请求排队等待，只会加剧竞争，没有业务价值。
```

```text
懂得方案取舍：抢单这类竞抢场景，适合快速失败，不适合请求排队等待。

1. 优化前为什么一定会超卖？
答：三点叠加：
① Redis 用多条命令判断，存在竞态；
② 分布式锁设置等待时间，请求排队穿透；
③ 数据库先查后改、无乐观锁 / 状态限制，并发更新全部生效，最终超卖。
2. 为什么把锁从「带等待」改成 tryLock(0)？
答：抢单是先到先得的竞争场景，同一订单已有请求在处理，后续请求等待没有业务意义；0 等待让请求快速失败，避免线程阻塞、请求堆积，提升系统整体吞吐。
3. 为什么全局 Redis Key 要改成 orderId 拼接？
答：全局 Key 所有订单共用，一个订单被抢就会删除 Key，导致全平台订单都无法抢单；按订单拆分后，标识互相隔离，只影响当前订单，业务正常运行。
4. 优化后为什么还要保留「锁前后两次 Lua 校验」？
答：防止锁释放瞬间，外部请求穿透进来再次执行抢单逻辑，双重校验进一步加固并发安全。
```

**排查和解决问题**
```text
二、五层架构逐层拆解（面试可直接背诵）
1. 接入 / 网络层（用户请求的第一道关卡）
核心职责：接收用户请求，做负载均衡、限流、路由、协议转换，把请求转发给后端应用层。
常见组件：Nginx、Tomcat、网关（Spring Cloud Gateway）、DNS、防火墙、CDN
常见问题：
网络波动 / 丢包：TCP 连接超时、跨机房延迟高、防火墙拦截
负载均衡不均：Nginx 轮询配置错误、后端节点权重设置不合理，导致部分实例压力过高
限流 / 熔断触发：QPS 超过网关限流阈值，导致请求被直接拒绝
协议 / 配置错误：HTTPS 证书过期、跨域配置错误、端口被占用
排查思路：
先看用户侧报错：是超时、502/504、还是直接无法访问？
用 ping/traceroute 排查网络连通性，用 curl/telnet 验证端口和服务状态
查 Nginx / 网关日志，看请求是否到达、转发到了哪个后端实例、是否被限流 / 拒绝
检查负载均衡配置、限流规则、证书有效期
优化手段：
多机房部署 + 异地多活，避免单点故障
网关层限流 + 应用层限流双重保障，避免流量直接打垮后端
静态资源走 CDN，减轻后端接入层压力
2. 应用层（业务逻辑的核心载体）
核心职责：处理业务逻辑，调用缓存、消息队列、数据库等组件，完成请求处理并返回响应。
常见组件：Spring Boot/Spring Cloud 微服务、Dubbo、线程池、JVM
常见问题：
服务不可用：实例宕机、进程退出、OOM 导致服务挂掉
性能瓶颈：线程池耗尽、CPU 飙高、GC 频繁导致请求处理慢
业务逻辑 bug：空指针、参数校验失败、事务处理异常
依赖调用超时：调用其他微服务 / 第三方接口超时，导致请求堆积
排查思路：
看应用监控面板：CPU、内存、线程池状态、GC 次数 / 耗时、接口响应时间
查应用日志：报错栈、异常信息、请求处理链路，定位是业务 bug 还是依赖调用问题
用 jstack 查线程死锁、jstat 查 GC 情况、jmap 导出堆快照分析 OOM
检查依赖服务的可用性，是否是下游服务挂了导致本服务超时
优化手段：
合理配置线程池，避免线程过多导致上下文切换频繁
微服务拆分，按业务域拆分服务，避免单体服务过大
异步化处理非核心逻辑，比如日志、通知、消息推送，用消息队列解耦
服务降级 / 熔断，依赖服务出问题时快速降级，避免连锁故障
3. 缓存层（高并发场景的 “第一道盾牌”）
核心职责：缓存热点数据，减轻数据库压力，提升接口响应速度。
常见组件：Redis、Memcached、本地缓存（Caffeine/Guava Cache）
常见问题：
缓存穿透：请求不存在的数据，直接打到数据库，导致数据库压力过大
缓存击穿：热点 key 过期，大量请求同时打到数据库
缓存雪崩：大量 key 同时过期，或者 Redis 集群宕机，导致所有请求直接打数据库
缓存一致性问题：缓存和数据库数据不一致，导致脏数据
Redis 性能瓶颈：单节点 CPU / 内存过高、连接数耗尽、主从同步延迟
排查思路：
看 Redis 监控：QPS、内存使用率、连接数、命令耗时、主从同步状态
查慢查询日志，看是否有大 key、热 key 导致 Redis 响应慢
看缓存命中率：命中率过低，说明缓存策略有问题，大量请求打到数据库
检查过期 key 分布，是否有大量 key 同时过期，导致缓存雪崩
优化手段：
缓存穿透：布隆过滤器拦截不存在的 key，或者给空值设置短期缓存
缓存击穿：热点 key 永不过期，或者加互斥锁（Redis 分布式锁）控制请求
缓存雪崩：给 key 设置随机过期时间，避免同时过期；Redis 集群部署，避免单点故障
缓存一致性：更新数据库后同步更新缓存，或者用 Canal 监听数据库 binlog 异步更新缓存
4. 消息队列层（系统解耦 + 削峰填谷的核心）
核心职责：异步解耦业务系统，削峰填谷，缓冲流量洪峰，保障系统稳定性。
常见组件：RabbitMQ、Kafka、RocketMQ
常见问题：
消息丢失：生产者发送失败、Broker 宕机、消费者消费失败且未重试
消息重复消费：网络波动导致 ack 失败，Broker 重复投递消息
消息堆积：消费者处理速度跟不上生产者发送速度，导致消息堆积，内存占用过高
顺序性问题：需要保证顺序的消息，被并发消费导致顺序错乱
排查思路：
看 Broker 监控：消息生产速度、消费速度、堆积数量、磁盘使用率
查 Broker 日志，看是否有消息发送失败、消费失败的记录
看消费者日志，是否有消费异常、重试失败的情况
检查消费者线程池配置，是否线程数过少，导致消费速度慢
优化手段：
消息丢失：生产者开启 confirm 机制，Broker 持久化消息，消费者手动 ack
消息重复消费：业务接口实现幂等性，用消息 ID 做唯一标识，避免重复处理
消息堆积：临时增加消费者数量，或者调整消费者线程池配置；优化消费逻辑，提升消费速度
顺序性问题：将顺序消息发送到同一个分区，用单线程消费该分区的消息
5. 数据库层（数据的最终落地层）
核心职责：持久化存储业务数据，处理数据的增删改查，保障数据一致性和可靠性。
常见组件：MySQL、PostgreSQL、Oracle
常见问题：
慢查询：SQL 未加索引、索引失效、大表关联查询，导致数据库 CPU 飙高、响应慢
锁冲突：行锁 / 表锁竞争，导致事务超时、死锁
主从同步延迟：主库写入频繁，从库同步延迟过高，导致读写分离时读不到最新数据
数据库连接池耗尽：连接数设置过小，大量请求等待连接，导致请求超时
排查思路：
看数据库监控：CPU、内存、磁盘 IO、连接数、慢查询数量
查慢查询日志，定位慢 SQL，用 explain 分析 SQL 执行计划，看索引是否生效
检查事务隔离级别、锁竞争情况，看是否有死锁、长事务
看主从同步状态，Seconds_Behind_Master 是否过高
优化手段：
慢查询优化：加合适的索引，避免 select *，减少大表关联，分页查询避免深分页
读写分离：主库写、从库读，减轻主库压力
分库分表：数据量过大时，按业务 / 时间分库分表，降低单表数据量
连接池优化：合理设置连接池大小，避免连接数过少导致等待
```

8  **幂等性：你项目哪里用到？**
```text
1. 什么是幂等
多次重复请求 / 消息执行，业务结果和执行一次完全一致，不产生脏数据、重复业务。
2. 本项目所有幂等场景 + 实现方案（按代码顺序）
场景 1：前端重复点击 / 接口重试（抢单接口幂等）
问题：用户重复点抢单、网络重试，同一司机多次请求同一订单。
实现（优化后）：
按订单维度的 Redis Lua 原子标识，订单被抢后 Key 删除，重复请求直接拦截；
Redisson 分布式锁互斥，同一订单串行执行；
数据库 状态 + 乐观锁 最终拦截重复更新。
优化前缺陷：仅靠简单 hasKey，高并发下无法保证接口幂等。
场景 2：Redis 删除标识操作幂等
问题：重复执行删除命令，可能报错或无效执行。
实现：Lua 脚本 先判断exists，再del，原子执行，删过就不再处理，天然幂等。
场景 3：MQ 重复投递（核心幂等场景）
问题：消费宕机、网络抖动、死信重试，RabbitMQ 重复推送同一条抢单消息。
实现：
消费端使用 订单状态 + Version 乐观锁 做条件更新：
第一次消费成功：状态改为已接单、版本号 + 1；
重复消息再次到达：状态 / 版本不匹配，更新行数为 0，直接放弃执行。
特点：利用现有业务字段实现幂等，无需额外建去重表，性能更高。
场景 4：死信队列定时重试幂等
定时任务拉取死信消息，复用同一套 状态+乐观锁 逻辑，重复重试不会重复抢单。
3. 总结背诵版
项目中幂等主要覆盖三大场景：
接口重复请求：Redis Lua 标识 + Redisson 分布式锁实现幂等防重；
Redis 删除操作：Lua 先判后删，保证原子与幂等；
MQ 重复消费 & 死信重试：数据库状态机 + 乐观锁实现最终幂等。
整套方案依托现有业务逻辑实现，轻量化、高性能，适配抢单高并发场景。
```

```text
主打：运行 Java 后端代码，解析 Servlet、Spring 等 Java Web 逻辑，处理动态接口。

一句话背诵版（面试直接说）
Tomcat 是开源轻量级 Java Web 应用服务器，也是 Servlet 容器，主要负责监听端口、接收并转发 HTTP 请求，运行 Java 后端程序。

1、Servlet 容器是什么？
一句话：Servlet 容器 = Java Web 程序的运行环境 + HTTP 请求的处理中心。

监听网络端口（比如 8080），接收浏览器 / 客户端发来的 HTTP 请求；

把 Java 代码的处理结果，再包装成 HTTP 响应，返回给客户端。
你熟悉的 Tomcat、Jetty，就是最主流的 Servlet 容器。

Tomcat 就像一个 “翻译官 + 调度员”：客户端说 HTTP 语言，你的 Java 代码说 Java 语言，Tomcat 负责把两者互相翻译、传递消息，让它们能正常对话。

你的 Java 项目，本质是运行在JVM上的；
Tomcat 是运行在 JVM 上的容器，帮你处理 HTTP 请求；
JRE 是 JVM 的载体，JDK 包含了 JRE 和开发工具。

一、先落地：你项目里 Tomcat 到底在哪？
你打包 jar → java -jar 启动
→ SpringBoot 自动启动了内嵌 Tomcat
→ 只是你没手动安装、配置、部署，所以感觉不到它存在。

Tomcat 就是一个跑在 JVM 里的 Java 程序，专门干两件事：
监听端口（默认 8080），接收浏览器 / Postman 发来的 HTTP 网络请求

二、Tomcat 核心组件（具象化，当成一个个 “模块实体”）
Tomcat 整体分两大块：Connector 连接器 + Container 容器
所有请求都按这个链路走，记这两个大模块就够了。
1. Connector 连接器（入口、网络层）
作用：负责网络通信、协议解析，相当于小区大门 + 门卫。
监听 IP + 端口（8080），建立 TCP 连接
解析 HTTP 协议：把浏览器发来的二进制流，转成 Java 能识别的 Request 请求对象
代码执行完后，把返回结果封装成 HTTP 响应，发回客户端
关键细节（面试常问）
内置线程池：每来一个请求，分配一条线程去处理（这就是 Tomcat 工作线程）
线程池满了 → 新请求排队 / 拒绝 → 出现接口超时、503（你排查五层架构里的经典问题）
2. Container 容器（业务调度层，Servlet 容器本体）
作用：管理 Web 应用、调用你的代码，相当于小区楼栋 + 住户。
容器内部又分层（从上到下）：
Engine：整个 Tomcat 引擎，顶层容器，管理所有站点
Host：虚拟主机（对应一个域名，比如 localhost）
Context：单个 Web 应用 —— 这就是你的乐尚代驾项目
一个 Context = 一个独立 Java Web 工程
Wrapper：包装 Servlet / SpringMVC 前端控制器，真正调用业务逻辑
完整请求流转（走一遍，立刻有实体感）
客户端（浏览器） → 网络
→ Connector（接请求、解析 HTTP、分配工作线程）
→ Engine → Host → Context（你的项目）
→ Wrapper → 调用 SpringMVC → 你的 Controller / 业务代码
→ 结果原路返回 → Connector 包装 HTTP 响应 → 客户端
形象比喻：
Connector = 快递驿站（收快递、分拣）
Container = 整栋楼
Context = 你家
请求 = 快递，一步步送到你手里，处理完再寄回去。
三、结合你的认知：Tomcat、JVM、SpringBoot 层级关系（彻底打通）
从最底层到最上层，一层套一层，再也不飘：
硬件 + 操作系统
JRE/JVM（Java 虚拟机，所有 Java 程序的运行底座）
Tomcat（本身就是一个大型 Java 程序，跑在 JVM 之上）
你的 SpringBoot 项目（被 Tomcat 加载托管，运行在 Tomcat 内部）
关键区分（你疑惑的点）
所有 Java 代码 最终都跑在 JVM
Tomcat 是中间载体：专门帮你接管 HTTP 网络请求，你不用自己写 Socket 监听端口、解析 HTTP 协议
SpringBoot 只是把 Tomcat 内嵌、自动配置，屏蔽了手动部署步骤，不是没有 Tomcat。
四、为什么招聘都要求会 Tomcat？你项目没用到，也要掌握什么？
你做 SpringBoot 开发，不用会手动部署 war、配置虚拟主机，但面试官考的是：

和 Nginx 分工：

2. 高频问题（线上故障 & 调优，和你五层排查模型联动）

五、极简背诵版（面试直接说，短而准）
```

**Nginx**
```text
Nginx 是什么？它和 Tomcat 的区别？
Nginx 是一个高性能的 Web 服务器 / 反向代理服务器，和 Tomcat 分工完全不同。
核心职责
反向代理：接收客户端请求，转发给后端的 Tomcat 集群，隐藏后端真实地址；
负载均衡：把请求均匀分配给多个 Tomcat 实例，避免单个实例压力过大；
静态资源处理：直接处理图片、CSS、JS 等静态文件，不用转发给 Tomcat，减轻后端压力；
限流、防攻击：配置访问控制、防 DDOS 攻击，保护后端服务。
Nginx vs Tomcat 核心区别
表格
特性	Nginx	Tomcat
主要用途	反向代理、负载均衡、静态资源	运行 Java Web 代码，处理动态请求
性能	高并发处理能力极强，适合处理静态请求	处理动态 Java 请求，并发能力弱于 Nginx
语言	用 C 语言开发	用 Java 开发，运行在 JVM 上
举个实际场景：
用户访问你的网站，请求先到 Nginx：
静态资源（图片、页面）直接由 Nginx 返回；
动态请求（登录、下单）转发给后端的 Tomcat，由 Tomcat 调用你的 Java 代码处理，再把结果返回给 Nginx，最后发给用户。

（1）正向代理（你上网翻墙那种）
角色：替客户端干活
举例：你（客户端）→ 代理服务器 → 目标网站
网站只看到代理 IP，看不到你真实 IP。
（2）反向代理（Nginx 干的事）
角色：替服务端干活，对外伪装成 “唯一入口”
流程：用户 → Nginx（入口）→ 后端多台 Tomcat
用户只知道 Nginx 地址，完全不知道后端有多少台 Tomcat、IP 是多少。
👉 这就是为什么叫反向代理：代理的是后端服务，不是客户端。
通俗比喻
正向代理：你找中介帮你买东西（中介帮你）
反向代理：店铺前台（Nginx）接待所有客人，再把订单分给后厨（Tomcat）（前台帮店铺）

3. 解答你的疑问：静态资源不是放前端吗？请求为啥先到 Nginx？
1）“静态资源放在前端” 是什么意思？
前端代码（html/js/css/ 图片）文件本身，确实是前端工程师写的。
但部署位置分两种：
单纯前后端分离：前端打包后丢到 Nginx 目录下
传统项目：静态资源打包在 Java 项目里，由 Tomcat 托管
线上最佳实践：静态资源一律交给 Nginx 处理
2）请求链路（线上标准流程，解释 “为什么先到 Nginx”）
用户在浏览器输入网址 / 点击接口：
请求先打到 Nginx（服务器第一层入口）
Nginx 判断请求类型：
静态资源（页面、图片、JS）：Nginx 自己直接返回，不走 Tomcat
→ 优点：Nginx 处理静态极快，不占用 Java 服务线程
动态接口（登录、下单、查数据）：Nginx 转发给后端 Tomcat
Tomcat 执行 Java 代码，结果原路返回
3）为什么不能让用户直接访问 Tomcat？（Nginx 不可替代的原因）
安全：隐藏后端真实服务器 IP，后端不直接暴露公网，减少被攻击风险
性能：静态请求全部剥离，Tomcat 只专心处理动态业务
集群扩容：多台 Tomcat 做集群，Nginx 统一做负载均衡
统一管控：限流、证书、防爬虫、黑白名单，全部在入口层统一配置
4. 结合你的项目：你本地不用 Nginx，线上必须有
本地开发环境
java -jar 乐尚代驾.jar → 内嵌 Tomcat 监听 8080
你直接访问 localhost:8080/接口，跳过 Nginx，完全没问题。
线上生产环境（真实上线架构）
公网用户 → 域名 → Nginx (80/443)
├─ 静态页面 / 图片 → Nginx 直接返回
└─ 后端接口 → 负载均衡 → 多台 Tomcat 实例 → 你的 SpringBoot 代码
```

```text
按作用域、技术领域划分，后端日常开发 & 面试高频池一共 5 大类，附作用、使用场景，区分清楚，不和 Tomcat 混淆。

分类

Spring 内置线程池、Dubbo/RPC 线程池、网关线程池
消息队列消费线程池
RabbitMQ/Kafka 消费者线程池，控制消费并发。
用途

RabbitMQ/Kafka 客户端连接池。

3. 对象池
复用大对象，减少对象创建、GC 压力，日常使用偏少。

场景：大实体、编解码对象、网络缓冲区对象。

Netty 内存池（ByteBuf 池）：网络 IO 框架核心
Nginx、Tomcat 底层缓冲区池
5. 其他小众池（了解即可）
任务池：存放待执行任务（常和线程池搭配）

数据库连接池（Hikari/Druid）
Redis 连接池
```

### **四、核心业务流程**

#### **1. 乘客下单流程**

```
1. 乘客输入起点终点 → web-customer
2. 调用 service-map 预估里程、价格
3. 调用 service-rules 计算详细费用（基础费+里程费+时长费）
4. 创建订单 → service-order（状态：待接单）
5. 发布订单消息 → RabbitMQ
6. service-dispatch 消费消息，推送给附近司机
7. 司机抢单成功 → 更新订单状态
8. 返回订单信息给乘客
```


#### **2. 司机抢单流程**

```
1. 司机监听附近订单 → web-driver
2. 调用 service-dispatch 获取可抢订单列表
3. 司机点击抢单
4. Redis 分布式锁防止超卖
5. 抢单成功 → RabbitMQ 通知 service-order
6. 更新订单状态为"已接单"
7. 推送司机信息给乘客
```


#### **3. 订单执行流程**

```
1. 司机到达起点 → 点击"确认到达"
2. 开始行程 → 点击"开始行程"
3. 实时上报位置 → MongoDB 存储轨迹
4. 到达终点 → 点击"结束行程"
5. 调用 service-order 计算最终费用
6. 生成支付订单 → service-payment
```


#### **4. 支付流程**

```
1. 乘客查看账单 → web-customer
2. 调用 service-payment 创建微信支付
3. 返回支付参数给微信小程序
4. 用户完成支付
5. 微信回调 → service-payment/wxPay/notify
6. 更新订单状态为"已完成"
7. 发放优惠券 → service-coupon
```

```java
}
```

### **七、常见问题应对**

#### **Q1: 为什么选择微服务架构？**

**A:**
- 业务复杂度高：代驾涉及乘客、司机、订单、支付等多个领域
- 团队协同开发：不同成员负责不同服务，降低耦合
- 弹性扩展：订单服务压力大时可单独扩容
- 技术多样性：某些服务可用 MongoDB，某些用 MySQL

#### **Q2: 如何保证分布式事务一致性？**

**A:**
- 使用 Seata AT 模式（自动补偿）
- 关键场景：下单扣减优惠券、订单创建+司机绑定
- 非关键场景：最终一致性（消息队列重试）

#### **Q3: 如何处理高并发抢单？**

**A:**
- Redis 分布式锁防止超卖
- RabbitMQ 削峰填谷
- 数据库乐观锁（version 字段）
- 前端防抖（3秒内只能点一次）

#### **Q4: 如何优化系统性能？**

**A:**
- Redis 缓存热点数据（司机信息、计价规则）
- MongoDB 存储位置轨迹（写入性能优于 MySQL）
- Feign 调用批量接口（减少网络往返）
- 异步处理非核心逻辑（发送通知、记录日志）
