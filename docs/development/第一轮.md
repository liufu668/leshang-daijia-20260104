**缓存三大问题（穿透 / 击穿 / 雪崩）你分别怎么解决？讲清楚方案和原因。**
为了防止缓存问题，我们项目针对订单预估缓存场景，做了三层针对性设计：
- 缓存穿透防护
  对不存在的经纬度路线，采用缓存空对象并设置 2 分钟短过期时间，避免无效请求重复穿透到地图、计费等第三方接口，从根源减少无效调用。
- 缓存击穿防护
  针对热点路线缓存失效的高并发场景，采用双重检查 + 轻量级 Redis 分布式互斥锁：
  先双重校验缓存状态，再通过 setIfAbsent 抢锁，保证同一时间只有一个请求回源计算；
  抢锁失败的请求直接降级返回系统繁忙，不阻塞、不等待，避免大量请求同时压垮第三方服务。
- 缓存雪崩防护
  在 15 分钟基础过期时间上，增加 **-1~3 分钟的随机偏移量 **，将缓存过期时间打散为 14~18 分钟，避免大量 key 在同一时间集中失效；

**RabbitMQ 你怎么保证消息不丢失、不重复、不乱序？**
_幂等性指同一个请求重复执行多次，最终业务执行结果和只执行一次保持一致，不会产生脏数据、重复业务。_
我们项目用 RabbitMQ 做抢单异步解耦，消息可靠性我从不丢失、不重复、不乱序三点保证：
第一，消息不丢失：
生产者端我用了 CorrelationData 开启发布确认机制，必须等 MQ 返回 ACK 才删除 Redis 抢单标识；
MQ 交换机队列消息持久化；
消费者关闭自动 ACK，数据库更新成功后手动 ACK，异常 Nack 重回队列，三层保证不丢。
第二，消息不重复：
我没有额外做消息 ID 去重，而是用数据库乐观锁 version + 订单状态做幂等。
第一个抢到的司机更新 version 并修改状态，重复消费的消息因为 version 不匹配，直接更新失败，天然实现不重复抢单。
第三，不乱序：
每个订单只会发一条抢单消息，且抢单队列配置单消费者，保证消息顺序。

**订单状态机是什么？MySQL 乐观锁怎么用在抢单里？**
1. 订单状态机
订单状态机并不是简单称呼订单有哪些状态，它代表了一整套流转规则,规定了订单状态只能按照固定流程正常流转。
规定了订单在什么状态下，执行什么操作才能切换为新状态，非法的状态变更会直接被拦截，以此保障业务流程正常执行。
2. 乐观锁
乐观锁会在数据表设置 version 版本字段，执行业务更新前先查询获取版本号，更新时比对数据库版本号。
版本匹配则更新数据并让版本号加一；
版本不匹配说明数据已被修改，更新失败。我们抢单业务就是依靠这种机制，解决高并发下订单超卖问题。
```text
虽然司机抢单那里看起来状态校验和乐观锁都是用来防止重复抢单，但二者作用层级不同并不重复。
状态机是业务层面做前置校验，拦截不符合条件的抢单请求；而乐观锁是数据库层面做并发兜底。
同时我们选用乐观锁替代了悲观锁，不会产生数据库行锁阻塞，减少了锁竞争开销，在高并发抢单场景下可以有效提升系统运行性能。
```

**HashMap 底层结构？1.7 和 1.8 区别？为什么线程不安全？**
HashMap 是 Java 集合里最经典的数据结构 + 并发问题缩影，能一次性考察你 4 大能力：基础、源码、算法、并发意识。
一、HashMap 底层结构
1. 整体结构
   JDK 1.7：数组 + 单向链表
   JDK 1.8：数组 + 单向链表 + 红黑树
2. 核心概念
   数组（哈希表 / 桶）：存储数据的主体，查询效率 O (1)，根据 key 的 hash 值计算下标定位元素。
   链表：解决哈希冲突（不同 key 算出来相同数组下标），拉链法存储。
   红黑树：1.8 新增，当链表长度 ≥ 8 且数组长度 ≥ 64 时，链表转为红黑树，查询效率从 O (n) 提升到 O (logn)。
3. 核心参数
   初始容量：默认 16
   加载因子：默认 0.75
   扩容阈值：容量 × 加载因子
   树化阈值：链表长度 ≥ 8
   树退化阈值：红黑树节点 ≤ 6 变回链表
二、JDK 1.7 和 1.8 的核心区别（面试必背 6 点）
表格
对比项	JDK 1.7	JDK 1.8
底层结构	数组 + 单向链表	数组 + 链表 + 红黑树

三、HashMap 为什么线程不安全？
HashMap 没有加任何锁，在多线程环境下会出现数据覆盖、数据丢失、死循环等问题。
1. 多线程 put 导致数据覆盖（最常见）
   线程 A 和线程 B 同时计算出相同数组下标。
   A 先插入元素，还没完成赋值。
   B 立刻也插入，直接覆盖 A 的数据，导致数据丢失。
2. JDK 1.7 扩容会造成链表环 + 死循环
   1.7 使用头插法，多线程并发扩容时，链表会反转。
   极端情况下形成环形链表，下次 get 查询时，程序无限循环，CPU 100%。
3. JDK 1.8 虽无环，但仍不安全
   1.8 用尾插法避免了环形链表，但：
   put 操作非原子性
   多线程同时扩容仍会数据覆盖
   size 计数不准确
总结：线程不安全的根本原因
HashMap 没有使用 synchronized / Lock 等任何锁机制，多线程并发修改时，无法保证操作的原子性、可见性、有序性。

底层结构
HashMap 底层是哈希表实现，JDK1.7 是数组 + 单向链表，1.8 优化为数组 + 链表 + 红黑树，链表长度≥8 且数组≥64 时转为红黑树，提升查询效率。

结构：1.7 无红黑树，1.8 加入；
插入：1.7 头插法，1.8 尾插法；
扩容：1.7 重新计算 hash，1.8 高位判断；

**sychronized 和 Lock 区别？分别使用场景？**
一、synchronized 和 Lock 核心区别（5 点必背）
底层实现
synchronized：JVM 内置锁，隐式锁，自动加锁释放
Lock(ReentrantLock)：Java 代码实现，显式锁，手动 lock ()/unlock ()
可中断性
synchronized：不可中断，抢不到锁一直等
Lock：可中断，lockInterruptibly() 可以放弃等待
公平锁 / 非公平锁
synchronized：只能非公平锁
Lock：可指定公平 / 非公平锁（默认非公平）
是否可尝试获取锁
synchronized：不能尝试，只能阻塞
Lock：tryLock() 尝试获取，拿不到直接走，不阻塞
Condition 精准唤醒
synchronized：wait()/notify() 随机唤醒
Lock：多个 Condition，可以精准唤醒某一类线程
二、原子性、可见性
synchronized：可见性 + 原子性 + 禁止重排，全能
Lock：底层 AQS+volatile，也能保证，但代码手动控制
三、使用场景（必背，结合你前面的题）
用 synchronized 场景
代码简单、锁粒度小（ConcurrentHashMap 1.8 锁桶头就是用它）
方法 / 代码块简短，自动释放锁，不会忘解锁
并发竞争不激烈，JDK 1.6 后锁优化（偏向锁、轻量级锁）性能很强
用 Lock (ReentrantLock) 场景
需要可中断、尝试获取锁、公平锁
长时间持锁、复杂逻辑，需要精准唤醒
高并发、竞争激烈，需要更高性能（AQS）
ConcurrentHashMap 1.7 的 Segment 用的就是 ReentrantLock
面试一句话口述版（直接背）
synchronized 是隐式内置锁，不可中断、只能非公平，自动释放；
Lock 是显式锁，支持可中断、尝试获取锁、公平锁、精准唤醒。
简单场景、小粒度用 synchronized；高并发、灵活控制、复杂场景用 Lock。

**死锁的四个必要条件？怎么避免？**
一、死锁四个必要条件（缺一不可，必须同时满足才会死锁）
互斥条件：资源只能被一个线程占用，别人不能抢
占有且等待：线程拿着自己的资源，还去等别人的资源
不可剥夺：别人不能强行抢走已占有的资源
循环等待：线程之间互相等待，形成闭环（A 等 B、B 等 C、C 等 A）
口诀：互斥、占有等待、不可剥夺、循环等待
二、怎么避免死锁（破坏任意一个条件即可）
破坏占有且等待：一次性申请所有需要的资源，不拿一半等另一半
破坏不可剥夺：拿不到资源就主动释放自己已占有的资源
破坏循环等待（最常用）：统一资源获取顺序，所有线程按固定顺序拿锁（比如先锁 A 再锁 B，永远不反过来）
互斥条件：大部分锁必须互斥，一般不破坏
三、面试口述一句话版
死锁四个必要条件：互斥、占有且等待、不可剥夺、循环等待。
避免死锁主要破坏后三个，最常用的是统一获取锁的顺序。

import java.lang.reflect.Method;

// 壳子：所有增强逻辑写这里
public class LogHandler implements InvocationHandler {

    // 持有真实对象
    private final Object target;

    public LogHandler(Object target) {
        this.target = target;
    }

    // 调用任何方法都会进这里
    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        // 【AOP前置增强】插入日志
        System.out.println("方法执行前：记录日志");

        // 执行真实业务方法
        Object result = method.invoke(target, args);

        // 【AOP后置增强】
        System.out.println("方法执行后：记录耗时");
        return result;
    }
}

**Spring 事务传播机制？讲 3 个常用的。**
A 方法有事务（开启了数据库事务环境）
A 调用 B 方法
A 的事务环境传给了 B → 这就是事务传播
事务像病毒 / 氛围，从外层方法传到内层方法，所以叫传播机制。
1、REQUIRED（默认）
有事务就加入，没事务就新建
外层有事务 → 跟着外层一起
外层没事务 → 自己开新事务
场景：绝大多数业务方法，默认就是它
2、REQUIRES_NEW
不管有没有外层事务，永远自己新开一个独立事务
外层回滚，不影响它
它回滚，也不影响外层
场景：日志记录、对账、不管主业务失败，日志必须入库
3、NESTED 嵌套事务
依附外层事务
外层回滚 → 内层一起回滚
内层单独回滚 → 不影响外层
场景：子流程出错只回滚自己，不毁掉整个大业务
极简面试口述
Spring 事务传播一共 7 种，常用三种：
REQUIRED 默认，有事务加入无则新建；
REQUIRES_NEW 始终新建独立事务，内外互不影响；
NESTED 嵌套事务，外层回滚内层一起回，内层可单独回滚。
```text
1.REQUIRED（默认：共用同一个事务）
@Transactional(propagation = REQUIRED)
public void 外层A(){
    // 开启事务
    内层B();
}

@Transactional(propagation = REQUIRED)
public void 内层B(){
    // 直接用外层A的同一个事务
    // A回滚 = B一起回滚
}
底层：同一个数据库连接，同一个事务
2.REQUIRES_NEW（独立事务，底层：挂起 + 恢复）
@Transactional(propagation = REQUIRES_NEW)
public void 外层A(){
    // 1.开启外层事务
    // 2.Spring自动【挂起外层事务】
    内层B();
    // 3.B执行完提交
    // 4.【恢复外层事务】继续执行
}

@Transactional(propagation = REQUIRES_NEW)
public void 内层B(){
    // 全新独立事务
    // B回滚，A没事；A回滚，B也没事
}
底层核心：
暂停外面事务 → 开新事务 → 用完恢复外面
3.NESTED 嵌套事务（底层：Savepoint 保存点！权限上下级）
@Transactional
public void 外层A(){
    // 开启大事务
    内层B();
}

@Transactional(propagation = NESTED)
public void 内层B(){
    // 不新开事务
    // Spring打一个【保存点savepoint】
    // 内层出错：只回滚到保存点，外层完好
    // 外层出错：全部一起回滚
}
一句话底层对比（面试必背）
REQUIRED：共用事务
REQUIRES_NEW：挂起外层 → 新建独立事务
NESTED：不挂起、不新建 → 打保存点
```

五、MySQL
**InnoDB 索引结构？为什么用 B + 树？**
InnoDB 索引底层是 B+ 树，主键索引是聚簇索引，叶子存整行数据，叶子节点双向链表相连。
不用二叉树：树太高，IO 多。
不用 B 树：非叶子存数据，一页索引少，树更高。
B + 树优势：
非叶子只存索引，树矮，磁盘 IO 少
叶子链表，范围查询快
查询 IO 次数稳定

**聚簇索引 vs 非聚簇索引？回表是什么？**
1. 先一句话定义
聚簇索引（主键索引）：叶子节点存整行完整数据，索引和数据在一起
非聚簇索引（二级索引 / 普通索引）：叶子节点只存主键值，不存整行数据
回表：通过二级索引拿到主键，再去主键索引查完整数据
2. 具象化伪代码（最关键！一看就懂）
① 聚簇索引（主键 id）B+ 树
// 叶子节点：直接存一整行
class LeafNode_PK {
int id;       // 主键
String name;
int age;
// 所有字段，完整数据
}
索引 = 数据，找到索引就找到整行。
② 非聚簇索引（比如 name 索引）B+ 树
// 叶子节点：只存主键，不存name、age
class LeafNode_Secondary {
String name;  // 建立索引的字段
int pk_id;    // 只存主键id，没有其他数据
}
找到 name，只能拿到 id，拿不到 name 以外的数据。
3. 回表是什么？（具象流程）
表：user(id(主键), name, age)
建索引：name 普通索引
SQL：select * from user where name = '张三'
执行流程（2 步 = 回表）
查非聚簇索引：找到 name = 张三 → 得到主键 id=10
回表：拿着 id=10，再去聚簇索引查完整行数据
回表 = 二级索引 → 拿到主键 → 再查主键索引
4. 覆盖索引：避免回表
如果 SQL：
select id,name from user where name='张三'
只查索引里有的字段（name+id）
→ 不用回表，直接返回。
5. 对比总结（面试必背）
聚簇索引（主键）
叶子存整行数据，索引和数据放一起，InnoDB 只有一个聚簇索引。
非聚簇索引（普通索引）
叶子只存主键，不存完整数据。
回表
二级索引查完，拿着主键再去聚簇索引查数据，叫回表。
覆盖索引
查询字段都在二级索引里，不用回表，性能最高。
6. 极简口述版（直接背）
InnoDB 主键索引是聚簇索引，叶子存整行数据；
普通索引是非聚簇索引，叶子只存主键；
通过普通索引查到主键，再去主键索引查询完整数据，这个过程叫回表；
覆盖索引可以避免回表。

**最左前缀原则？联合索引怎么建？**
最左前缀原则：联合索引查询必须从最左侧字段开始，不能跳过左侧字段。
联合索引建立原则：高频在前，等值在前、范围在后，区分度高在前。
遇到范围查询，后面字段索引失效。

**MySQL 事务隔离级别？默认是什么？解决了什么问题？**
一、4 个隔离级别（从低到高）+ 3 个问题
先记 3 个脏问题：
脏读：读到别人未提交的数据
不可重复读：同一事务内，两次读不一样（别人改了并提交）
幻读：同一事务内，数量变了（别人新增 / 删除并提交）
二、4 个隔离级别（InnoDB 默认第 3 个）
1. 读未提交 READ UNCOMMITTED
能读到别人没提交的数据
问题：脏读、不可重复读、幻读 全都有
几乎不用
2. 读已提交 READ COMMITTED（RC）
只能读别人已提交的数据
解决：脏读
剩下：不可重复读、幻读
Oracle 默认，MySQL 不默认
3. 可重复读 REPEATABLE READ（RR）【MySQL 默认！】
同一事务内，多次读结果一致（靠 MVCC 快照）
解决：脏读、不可重复读
剩下：幻读（InnoDB 用间隙锁解决了幻读）
4. 串行化 SERIALIZABLE
最高级别，加锁串行执行
全部问题都解决
性能极差，几乎不用
三、一句话极简背诵（直接背）
隔离级别：读未提交 → 读已提交 → 可重复读 → 串行化
MySQL InnoDB 默认：可重复读（RR）
解决问题：
RC：解决脏读
RR：解决脏读、不可重复读，InnoDB 靠间隙锁解决幻读
串行化：全解决

**慢查询怎么排查？explain 看哪些字段？**
一、慢查询排查步骤（面试直接背）
开启慢查询日志
slow_query_log = ON
设置阈值：long_query_time = 1（超过 1 秒就是慢 SQL）
查看慢日志，定位耗时 SQL
用 explain 分析 SQL 执行计划
优化：加索引、避免回表、避免索引失效、优化 join
二、explain 重点看 6 个字段（必背，最核心）
1. type（最重要！看索引好不好）
性能从好到差：
system > const > eq_ref > ref > range > index > ALL
ALL：全表扫描，最差，必须优化
range：范围查询（> < between），正常
ref：普通索引，正常
eq_ref：主键 / 唯一索引，最好
2. key（实际用到的索引）
NULL：没用到索引，要建索引
显示索引名：用到了该索引
3. rows（扫描行数）
越小越好，行数大说明扫描太多，索引不行
4. Extra（额外信息，坑最多）
Using filesort：文件排序，没用到索引排序，必须优化
Using temporary：用到临时表，严重问题
Using index：覆盖索引，不回表，最优
Using where：存储引擎层过滤，正常
5. possible_keys（可能用到的索引）
理论上能用的索引，key 为空但这里有，说明索引失效
6. id
查询顺序，多表 / 子查询时看执行顺序
三、一句话极简背诵版
慢查询先开慢日志，定位慢 SQL 后用 explain 分析；
重点看 type、key、rows、Extra；
type 避免 ALL 全表扫描，Extra 避免 Using filesort/Using temporary，Using index 是最优覆盖索引。
四、通俗大白话
type=ALL：全表扫，完蛋
key=null：没索引，完蛋
Using filesort：排序没走索引，完蛋
Using index：覆盖索引，最棒

5. ZSet 有序集合（跳表 + 哈希）
底层：跳表，自动排序，不重复，带 score 分数
场景
排行榜：积分、销量、热度排名
延时队列（score 存时间戳）

String：缓存、计数器、分布式 ID

**Redis 持久化 RDB 和 AOF 区别？**
一、一句话核心区别
RDB：定时全量快照，二进制文件，压缩小，速度快，可能丢数据
AOF：实时记录命令日志，文本格式，数据安全，文件大、重放慢
二、详细对比（面试必背，精简版）
1. 存储方式
RDB：把内存数据整体 dump 成二进制文件（快照）
AOF：记录每一条写命令，追加到日志文件
2. 触发方式
RDB
手动：save、bgsave
自动：配置定时快照（如 900 秒 1 次）
AOF
实时追加：每次写命令就记录
三种策略：
always：每条都刷盘，最安全最慢
everysec：每秒刷盘（默认，折中）
no：交给系统，可能丢数据
3. 数据安全性
RDB：定时备份，两次快照之间宕机 → 丢数据
AOF：everysec 最多丢 1 秒数据，always 几乎不丢
4. 恢复速度 & 文件大小
RDB：文件小、恢复极快
AOF：日志越来越大，恢复慢；可 bgrewriteaof 重写压缩
5. 性能
RDB：fork 子进程，主线程几乎不阻塞，性能好
AOF：频繁 IO，性能略差
三、使用场景
RDB：适合冷备份、容灾、大数据量恢复
AOF：适合高可用、要求少丢数据
生产环境：RDB + AOF 同时开启，AOF 优先恢复，RDB 做兜底备份
四、极简背诵版（直接背）
RDB 是定时全量快照，文件小恢复快，但可能丢数据；
AOF 是追加写命令日志，数据更安全，文件大恢复慢；
生产一般两者同时开启，AOF 优先恢复。

**分布式锁怎么实现？Redisson 原理？**
一、原生 Redis 分布式锁（SETNX）实现 + 问题
1. 核心命令（必须原子）
redis
SET lock_key uuid NX EX 30
NX：不存在才设置（加锁）
EX：过期时间 30 秒（防死锁）
uuid：唯一标识，只能自己解锁
解锁（Lua 脚本，保证原子性）
lua
if redis.call('get',KEYS[1]) == ARGV[1] then
return redis.call('del',KEYS[1])
else
return 0
end
2. 原生锁 4 个致命问题
锁超时，业务没执行完 → 别人抢锁，并发安全问题
不可重入：同一个线程拿不到第二次锁
不可重试：抢不到直接失败
主从切换：主节点挂了，锁丢失
二、Redisson 原理（面试重点，通俗 + 核心）
1. 底层解决了上面所有问题，核心 3 个机制
① 可重入锁（利用 Hash 结构）
plaintext
lock_key: {
threadId: 重入次数
}
同一个线程再次加锁，次数 + 1；解锁 - 1，次数为 0 才删除。
② 看门狗（自动续期，解决业务超时）
加锁成功后，后台定时线程（看门狗）每 10 秒续期（默认过期 30s）
业务没执行完 → 自动延长过期时间
业务执行完 → 停止续期
③ 可重试、阻塞抢锁
用发布订阅：抢不到锁就订阅，释放锁时通知，避免自旋空耗 CPU。
④ 主从锁丢失问题 → Redlock（红锁）
向多个独立 Redis 主节点同时加锁，过半成功才算加锁。
三、极简背诵版（直接背）
原生 Redis 锁：用 SET key uuid NX EX 加锁，Lua 脚本解锁；存在超时释放、不可重入、不可重试、主从丢失问题。
Redisson 原理：
基于 Hash 实现可重入；
看门狗自动续期，解决业务超时；
发布订阅实现阻塞抢锁；
红锁 Redlock 解决主从切换锁丢失。

**缓存和数据库一致性怎么保证？**
一、核心结论先记住
没有绝对强一致，只能做到最终一致；优先保证：读多写多用「Cache‑Aside 旁路缓存」，写操作用「先更库、再删缓存」
二、4 种方案对比（面试必背）
1. 先更新数据库，再更新缓存（❌不推荐）
问题：
并发下：A 更新库、B 更新库 → 缓存更新顺序错乱，脏数据
缓存频繁更新，浪费性能
2. 先更新缓存，再更新数据库（❌完全不推荐）
数据库更新失败 → 缓存是新的、库是旧的，直接不一致
3. 先更新数据库，再删除缓存（✅标准方案，Cache‑Aside）
流程：
更新数据库
删除缓存
下次查询自动从库查最新数据写入缓存
会有啥问题？
极小概率：线程 A 查缓存过期 → 查库；线程 B 更新库 + 删缓存；A 把旧数据写回缓存 → 脏数据
解决：延迟双删
更新库 → 删缓存 → 休眠 500ms 再删一次缓存
4. 先删缓存，再更新数据库（❌不推荐）
线程 A 删缓存；线程 B 查询写入旧缓存；A 更新库 → 缓存永远脏数据
三、高并发强一致方案（终极）
Canal 订阅 binlog
数据库更新 → binlog 变更 → Canal 监听 → 删除 Redis 缓存
优点：异步、不侵入业务、性能好
分布式锁
更新数据库 + 删缓存全程加锁，强一致，性能低
四、面试极简背诵版（直接背）
缓存与数据库一致性常用先更库再删缓存；
并发脏数据问题用延迟双删解决；
高并发场景用 Canal 监听 binlog 异步删缓存；
不推荐先更缓存或先删缓存。
五、伪代码（具象化）
// 正确：先更库，后删缓存
updateDB();
delCache();
// 延迟双删
Thread.sleep(500);
delCache();

**SpringCloud 组件：Gateway、Feign、Sentinel 作用？**
1. Gateway（网关）
作用：请求入口，统一拦截、路由、鉴权、限流、日志

路由转发到对应微服务

**服务雪崩怎么解决？**
一、什么是服务雪崩
下游服务挂了 → 上游大量请求堆积、线程耗尽 → 上游也挂了 → 连锁反应，整个系统瘫痪
通俗说：一个崩，全崩。
二、4 大核心解决方案（直接背）
1. 熔断（Sentinel / Hystrix）
下游异常率过高，直接拒绝调用，快速失败，不等待
切断故障传播，防止拖垮自己
2. 降级
非核心服务暂时关闭、返回兜底数据（静态页、默认值）
保住核心业务正常运行
3. 限流（Gateway + Sentinel）
限制 QPS，控制每秒请求量
防止大量请求打垮服务，削峰
4. 超时控制 + 线程池隔离
设置调用超时时间，不无限阻塞
不同服务用独立线程池，一个崩了不影响其他
一句话极简背诵
服务雪崩是下游故障导致上游连锁瘫痪；
解决靠 熔断、降级、限流、超时隔离，常用 Sentinel 实现。

**Feign 调用怎么传递请求头？怎么处理异常？**
一、Feign 传递请求头（2 种常用方式，必背）
方式 1：注解直接加（静态固定头）
@FeignClient(value = "user-service")
public interface UserFeign {
@GetMapping("/user/get")
@RequestHeader(value = "token", required = false)
UserDTO getUser(@RequestHeader("token") String token);
}
缺点：每个接口都要写，不通用。
方式 2：拦截器全局传递（最常用，自动透传）
核心：实现 RequestInterceptor，把当前上下文 header 塞进去
@Component
public class FeignHeaderInterceptor implements RequestInterceptor {
    @Override
    public void apply(RequestTemplate template) {
        // 从当前请求上下文拿token
        ServletRequestAttributes attributes = (ServletRequestAttributes) RequestContextHolder.getRequestAttributes();
        if (attributes != null) {
            HttpServletRequest request = attributes.getRequest();
            String token = request.getHeader("token");
            template.header("token", token);
        }
    }
}
⚠️ 注意：开启 hystrix 时要设置线程上下文传递
yaml
feign:
hystrix:
enabled: true
hystrix:
command:
default:
execution:
isolation:
strategy: SEMAPHORE # 信号量模式，共享主线程上下文
二、Feign 异常处理（2 种方案）
方案 1：Feign 自带异常解码器（全局统一处理）
实现 ErrorDecoder，解析远程服务返回的异常信息，抛出自定义异常
@Component
public class FeignErrorDecoder implements ErrorDecoder {
    @Override
    public Exception decode(String methodKey, Response response) {
        // 解析响应状态码、body，抛出自定义业务异常
        return new BusinessException("远程调用失败：" + response.status());
    }
}
方案 2：熔断降级（Sentinel/Hystrix），兜底处理
写降级类实现 Feign 接口
@Component
public class UserFeignFallback implements UserFeign {
    @Override
    public UserDTO getUser(String token) {
        // 异常/超时直接返回兜底数据
        return new UserDTO(-1L, "服务暂时不可用");
    }
}
Feign 注解指定 fallback
@FeignClient(value = "user-service", fallback = UserFeignFallback.class)
public interface UserFeign {
}
三、极简背诵版（面试直接说）
传递请求头：用 RequestInterceptor 拦截器全局透传；开启熔断要切换为信号量隔离。
异常处理：
全局异常：自定义 ErrorDecoder；
熔断兜底：配置 fallback 降级类，返回兜底数据。

八、场景设计题（真实面试必考）
**如果让你重新设计代驾抢单系统，1000 个司机同时抢 1 个订单，你怎么保证：不超卖,高性能,高一致,不重复接单**
用 Redis + Lua 原子抢单，完全去掉分布式锁竞争，MQ 异步落库最终一致，DB 只做兜底，不参与并发争抢。
一、重新设计后的完整流程（最标准）
1. 用户发单
订单写入 DB
Redis 写一个抢单标识（order_accept:orderId = 1）
推送给附近 1000 个司机
2. 1000 司机同时抢单（核心）
直接走 Redis + Lua 脚本，原子抢单
不使用分布式锁！不使用锁！
Lua 脚本逻辑（原子性，天然只有 1 人成功）：
lua
-- KEY[1] = 订单标识
-- ARGV[1] = 司机ID
if redis.call("get", KEYS[1]) == "1" then
redis.call("set", KEYS[1], "0")  -- 关闭抢单
redis.call("hset", "order_winner", KEYS[1], ARGV[1]) -- 记录中奖司机
return 1  -- 成功
else
return 0  -- 失败
end
为什么比你现在代码好？
无锁设计
1000 并发也只有 1 人成功
Redis 单线程原子执行，绝对不超卖
性能比分布式锁高 10~50 倍
3. 抢单成功 → 发送 MQ
不同步等待 MQ（你现在代码同步等待 MQ 是性能瓶颈）
MQ 异步更新 DB 订单状态
4. MQ 消费者更新数据库
更新司机 ID
更新订单状态
DB 唯一索引做最终兜底
5. 前端 / 司机端实时推送结果
成功：推送已抢到
失败：推送已被抢走
二、你现在代码的 4 个可优化点（面试可以主动说，加分）
1. 分布式锁 Redisson 没必要
抢单不应该用锁，应该用 Redis 原子操作
锁会产生：
锁竞争
锁等待
锁释放
高并发下性能差
2. 同步等待 MQ ACK 不适合高并发
你现在：
plaintext
correlationData.getFuture().get(5, TimeUnit.SECONDS);
同步等待 MQ = 高并发下直接卡死
抢单必须异步化，不能同步等待。
3. 两次 Redis 判断多余
exists + 锁内二次判断
Lua 脚本一次原子判断就够
4. 删 Redis 标识多余
Lua 里直接把 order_accept:123 = 0
代表不可抢，不用删。
三、重新设计后，如何保证 4 个目标？
1）不超卖
Lua 原子抢单，天然只允许一个人成功
2）高性能
无锁
全内存操作
Redis 抗 10w QPS
MQ 异步削峰落库
3）高一致
Redis 抢单强一致
MQ 确保消息可靠投递
定时任务校对 Redis + DB 最终一致
4）不重复接单
Redis 状态位控制
DB 唯一索引兜底
订单一旦被抢，立刻关闭
四、面试口述最终答案（直接背）
如果我重新设计代驾抢单系统，我会这样做：
用户下单后，订单入库，并在 Redis 中标记可抢单状态。
